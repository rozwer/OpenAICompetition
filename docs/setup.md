# ローカル起動

必要環境：Node.js 24以上、pnpm 10.33.0。Codex CLIはプロジェクト依存として0.153.4を固定する。
Macでも同じコマンドを使う設計だが、この版はWindowsで検証する。

```sh
pnpm install --frozen-lockfile
pnpm exec codex login
pnpm dev
```

`http://127.0.0.1:3000`を開き、利用者Aで開始する。
ChatGPTでログインする。既にログイン済みなら`pnpm exec codex login status`で確認する。
AIモデルはCodexの既定設定。必要なら`.env.local`の`CODEX_MODEL`で指定する。
プロジェクト内のCodexを優先し、その他は`CODEX_BINARY`に実行ファイルのパスを指定できる。
アプリはChatGPT認証を確認し、APIキーへの切替は行わない。

## 最初に試す流れ

1. 「散歩を再生」。架空の位置記録がSQLiteに保存され、20m以内の街が解放される。
2. 場所のマーカーを選ぶか、地図全体について文字で話す。
3. 原文が保存され、Codexが応答する。失敗した場合は理由と再試行を表示する。
4. 左下の人物アイコンから「自分について」を開き、抽出された記憶・根拠を確認して訂正。
5. 別のブラウザプロファイルで利用者Bを開く。AからYOKOHAMA-Bへ申請、Bが承認する。

`.local/grow-map.sqlite`に保存。再起動しても残る。`.local`はGit管理外。
同じブラウザの複数タブはCookieを共有するので、A/Bの同時操作には別プロファイルを使う。
アプリのAI処理は開発で使うCodexと同じアカウントの利用枠を消費する。

## 実GPS

アップロードボタンからGPXまたはJSONを選ぶ。最大2MB、1万点。
共通JSONは配列、または`{"points":[...]}`形式。

```json
[{"id":"record-001","lng":139.65,"lat":35.44,"time":"2026-09-05T07:00:00Z","accuracy":8,"origin":"imported"}]
```

精度不明は`accuracy:null`。同じIDは重複取込みしない。時刻はタイムゾーン付きISO 8601。
GPXには時刻付きtrkptが必要。測位精度が分からないGPXは保存のみで、通行済み・解放の根拠にはしない。
現在地ボタンで前景記録を開始・停止。画面を消した状態での記録は保証しない。

## iPhone・同じPCに接続する別端末（未検証）

通常はlocalhost限定。外部端末で試すときは`.env.local`へ`DEMO_ACCESS_CODE`を設定し、
`pnpm exec next dev --hostname 0.0.0.0`でLAN待受けに変更する。
接続した端末でコードを入力してデモA/Bを選ぶ。コードは発表者用で、一般利用者の本人認証ではない。
LANからのGPSにはHTTPSが必要。信頼されたHTTPS接続の設定は未実施。
App Server、DB、Codexの資格情報をLANに直接公開しない。
外部公開向けホスティングはこの手順の対象外。

## 確認コマンド

```sh
pnpm check
pnpm build
pnpm test:e2e
```

E2Eはインストール済みChromeを使う。先にbuildする。3001番で独立サーバーを起動し、毎回別の`.local/e2e-*.sqlite`へ架空A/Bのデータを追加する。
モバイル幅のテストは390×844。実機やエミュレーターでの検証とは分けて記録する。
完全な7機能デモの既存受入条件すべてが合格した状態ではない。

## AIが選んだ経由地を通る徒歩ルート

1. https://account.heigit.org/ でopenrouteserviceのAPIキーを取得する。
2. リポジトリ直下の `.env.local` に `ORS_API_KEY=取得したキー` を設定する（ブラウザやチャットへ貼らない）。
3. Next.jsサーバーを再起動する。PC・LANの両方を起動している場合は両方再起動する。
4. 地図全体または場所ごとの会話で好みを伝え、「この会話から散歩ルートを作る」を押す。
5. 出発地・目的地と任意の必須経由地を選択し、作成する。GPS出発は精度50m以内の5分以内の実測のみ。

APIキー未設定でもAIの立ち寄り先提案は作成・保存するが、道順は表示しない。キー設定後、同じ会話・条件で再作成すると保存済みの提案から徒歩経路の取得を再試行する。
当初の候補は既存の横浜3地点。施設検索・入口データ整備は今後追加する。経路の地点は100m以内の道路へスナップし、応答のway_pointsで順序と距離を検証する。ORＳへの送信は座標のみで、会話内容や認証情報は送らない。
経路APIが失敗した場合、直線などの代用を作らない。時間は徒歩移動の推定で立ち寄り時間を含めない。
