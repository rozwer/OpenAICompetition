# 次回実装の共通受入

この文書は本番計画の仕様です。リハーサルの過去の合格条件を後から変更するものではありません。
担当者、Issueのopen/closedにかかわらず同じ境界を適用します。
最初に一度読み、各Issueは該当する条件だけを参照します。8項目を全Issueで8回テストする指示ではありません。

## C1 原文・本人状態・版

原文と本人のconfirmed/rejected等を保存し、計算結果の再生成で上書きしません。
読取りとapplyは現在のnamespace・actor・参照版・許可を照合します。
訂正は正本更新、遅着jobの状態条件更新、派生の読取り時照合、通知を分担します。
汎用失効基盤を新設したり、別moduleの全tableを推測更新したりしません。

## C2 非同期の取消と再入場

画面の現在scopeと取得scopeが違う結果は、render・decode・applyの各該当境界で採用しません。
AbortSignalと完了時の現行性検査を使い、A→B→Aでも古いAのrequestを再採用しません。
同じscopeのresetでも旧結果を失効させます。React StrictModeのcleanupを利用者向け失敗表示へ変換しません。
request identity・generation等の方法は既存実装に合わせ、全moduleへ新しい共通機構を強制しません。
基盤担当が「scope切替／A→B→A／unmount後完了／同scope reset」を一組で確認し、各操作はその結合部分の反例だけを追加します。

## C3 namespace表と保存単位

namespace対象tableを追加するときは、schema/migration、生成器、列対応、clone/reset、export、共有、delete/purgeの対象または除外理由を同時に宣言します。
schemaから対象表を列挙して宣言漏れを検出し、外部キー順序、他scope不変、seed完全性、変更通知保持を確認します。
resetはDBをclose/reopenして旧対象行が残らず必要なseedが戻ることを確認します。
一般exportは他者のprivate entity、健康値・由来不明の派生を含めません。既知非健康を維持し、除外件数・理由・partialを返します。
外部provider I/Oはtransactionの外で行い、取消・版競合後に遅着bytesや結果を確定しません。

## C4 capabilityと実行証拠

catalog、service、実handler、対向manifest、build、provider証拠が一致した範囲だけを利用可能にします。
fixture/未接続/未設定を成功に昇格させず、任意枝の不足で既存の通常操作まで閉じません。
基盤担当が重複登録・未解決service・fixture混入・対向manifest/build/provider不一致の拒否を共通で確認します。
各操作は必要なcapabilityの集合と不足時の表示だけを確認します。
receiptはその操作を実行した証拠、既存manifest、同じ製品buildRevisionに結び付けます。任意の文字列や生成JSONだけで発行しません。
新しい恒久receipt管理システムは作らず、既存の発行・検証経路を使います。

## C5 UIから実API・DB・再表示

利用者が操作を始め、保存成功を確認し、画面再入場またはDB再open後に同じ結果を読めるところまでを操作Issueの完了にします。
返却IDだけ、静的見本だけ、注入fakeだけを完了にしません。HTTP形式・operation ID・binary/MIMEを実境界で照合します。
moduleの内部チェックリストは同じIssueに置きます。接続を後回しにするためだけのINTを追加しません。
共有kernelや外部provider/native接続が独立する場合は、その実在する依存と未接続範囲を本文へ明記します。

## C6 未知・出典・利用者の確認

unknownをゼロ、成功、訪問済み、道路通行可、素材利用許可へ変換しません。
候補の閲覧・保存・GPS近接から本人の訪問確認や建物成長を起こしません。
AIへは現在許可された最小の原文・根拠だけを解決して渡し、固定結果や別providerへ無断切替しません。
相棒のimport・候補採用・profile選択は別の利用者操作のまま保持します。Issue統合を理由に自動選択へ変更しません。

## C7 検証の責任

| 層 | 担当が確認すること | 重複させないこと |
|---|---|---|
| 共有基盤・kernel | 型、境界、共通反例、標準runnerで収集できること | 各画面で共通反例一式を再実行しない |
| 操作Issue | 固有の画面→API/DB→再表示を一経路と固有の失敗例 | 内部moduleごとに追加INTや全製品検査を置かない |
| release/GATE | 代表的な連続操作、必要な実provider/実機、buildの組合せ | 個別機能の全入力組合せを再試験しない |

runtime・build設定・共有契約の変更には影響する標準check/buildを行います。
通常は対象検査で十分な差分へ、無関係な全検査を積み上げません。
再実行は新しい変更、失敗、環境差、欠けた証拠が理由です。レビューは既存ログと対象commitを照合し、必要な反例だけを追加します。
Node/VitestとBun固有suiteを明示分離し、file workerへ一時DBを与えます。実file DBの再open確認は残します。
運用checkの合格を製品の合格と報告しません。

## C8 発見から修正

学びは事実、最小再現、原因または仮説、仕様の一文、反映先Issue、拒否例をまとめます。
完了済みIssueの発見も本番用の本文へ戻し、過去の証拠はリンクで残します。
開始時の既知pathをまとめて取得し、同じ操作の配線不足はそのIssueへ戻します。
画面や利用者操作の意味を変える案だけは、具体例を示して判断を求めます。

版directoryを変更する場合は、旧版のlockで覆えると推測せず、新しい全pathを取得してから編集する。

## 今回のレビュー知見の適用

[レビュー前に仕様へ固定すること](REVIEW_PREVENTION.md)はC1/C2/C5/C7/C8の具体例である。既定ID・復元草稿は実decoderへ通し、保存中の追記と旧Promiseの実完了を確認する。
レビューは対象head・差分・コマンド・終了結果・証拠・未接続を一組で受け取り、宛先を照合する。修正後は影響する反例を確認し、同じ証拠の反復収集をしない。
計画再編は要件対応・独立枝の待ち条件・生成物・実行台帳・未登録を含むIssue全件まで照合する。過去の完了と新しい操作単位の完了を混同しない。

外部資料の掲載者と著者・作成機関を分け、固有事実の根拠箇所を記録する。検査対象は未追跡ファイルを含む提出変更と一致させ、commit後はclaim base..headの差分を照合する。
