# レビュー前に仕様へ固定すること

2026-09-10。今回の差し戻しと作業の往復から、次の実装へ持ち込む条件を定める。
既存の製品要件と本人操作は変更しない。
共通の反例は所有する基盤で一度確認し、各操作Issueは自分の接続部分と固有の失敗例を確認する。

## 既定経路と保存中の操作

注入した有効値だけでは、利用者が通常操作で生成する値を検査できない。
IDは注入なしの生成、cryptoを使えないfallback、保存草稿からの復元を製品のHTTP decoderへ通す。
JSON bodyの原文は非破壊で検査し、query等の型変換と分ける。
HTTPの既知errorは契約statusを維持する。

非同期操作はscope文字列に加えrequest identityを照合する。
A→B→A、同scope reset、unmount後の旧Promiseを実際に完了させ、旧結果が採用されないことを確認する。
草稿保存は送信時snapshotと成功時の最新draftが一致するときだけ消去する。
待機中の追記は未送信のまま残し、再入場して選択・コピーできる。
これらはR01/R04/R06と共通受入C1/C2/C5を具体化した条件である。

## 提出する実装と証拠を揃える

UIの操作確認は製品のReact部品をmountし、利用者操作がcallbackとstate変更へ到達することを確認する。
複製した静的HTMLや画像だけを操作の合格にしない。
StrictModeのcleanupは取消として処理し、失敗通知にしない。
テストは標準runnerの命名・配置・環境指定で収集できるものを提出する。

レビュー依頼にはTask/Issue、PR、worktree、対象head、差分範囲、実行コマンド、終了結果と証拠path、未接続、既知失敗を一組で渡す。
送信前に宛先の役割とTask IDを照合する。
レビュー結果には確認したheadと指摘位置・再現条件を残し、修正後は変わった範囲と反例を照合する。
同じheadの有効なログは再利用する。
古いheadの結果は変更箇所への影響を確認して使い、現在headを検査したと記載しない。
共通checkの再実行は新しい変更、失敗、環境差、欠けた証拠が理由のときに限る。

## 出典と検査対象を明示する

外部資料は掲載サイトと著者・作成機関を区別し、固有事実がどの資料のどの記載に基づくかを残す。
URLだけを付けて掲載者へ著者帰属を置き換えない。
検査の対象集合は今回提出する変更に合わせる。
未追跡ファイルを含む提出前は対象を明示して確認し、commit後の提出証拠はclaim baseから対象headまでの差分と照合する。
作業treeのdiffが空でも、提出変更を全件検査した証拠にはならない。

## 着手前に範囲と接続責任を決める

Issueには利用者の開始操作、保存結果、再表示、既存DTO/Port/operation、既定値、未対応時の表示、必要なproviderを先に書く。
内部配線は同じ操作の実装範囲へ含め、既存SDKや共通resolverを二重実装しない。
次回本番の操作単位と、リハーサルで完了済みのmodule受入を混同しない。

既知の編集pathは文書・生成物・版directoryを含めて開始時に全取得する。
古いIssueのpathと現在の配置規則が衝突するときは、編集前に生成元とpathを修正して取得する。
完了済みの定義は変更せず、必要な残作業の指示へ戻す。
開始失敗は保存receiptと同じprocessの最終結果で状態を確認し、二重claimや時刻だけのlock回収で解決しない。
開始済みclaimの終了に失敗した場合は、旧起動経路のreceipt所在と現在tokenの一致を確認する。開始失敗と終了失敗を分けて記録する。

## 再編の完了条件

タスク数を減らすときは、先に「操作→保存→再表示」の所有範囲と共有基盤を定める。
元の要件・受入・operationの所有を対応表で保持し、独立して完成できた枝に新しい待ちを増やさない。
今回のnativeは共通健康基盤を必要とするが、XML入力やAIの完成は待たない。

計画の写しを作っただけでは実行計画の差し替え完了にしない。
変更対象の正本、生成Issue、共有済みdevelop、台帳、GitHub全件を照合する。
台帳にない発見と、doneなのにopenの表示不整合も対象に含める。
移管はsuperseded、実装完了はdoneと区別し、元本文・完了履歴・提出commitを残す。
実行中・提出済みの定義を変更せず、CAS拒否や通信失敗時は未反映箇所だけを再実行する。
