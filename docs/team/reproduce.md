# 4人のCodexで再現する手順

最初の版の再現手順。全7機能を4時間で再現できたという検証はまだ行っていない。
事前資産の持込み可否は大会案内で確認する。仕様・手順から空リポジトリへ再現する前提。

## 固定する構成と依存方向

```text
src/app                    統合画面とHTTP受付（組立て担当のみが変更）
  → src/features/*         各機能のUI
  → src/server             アプリケーション処理・接続の組立て
src/features/* → src/contracts, src/domain, src/client
src/server → src/contracts
src/infrastructure → src/contracts
src/domain → src/contracts
src/contracts → zod
```

`server/services.ts`は組立て箇所としてSQLite/Codexの具象実装を注入する。
機能同士のimportは禁止。画面間の受渡しは`FeatureContext`。
依存方向は`pnpm check:boundaries`で検証する。
`contracts`、依存追加、ロックファイル、`app`、DB変更は統合担当が調整する。
同じDBに全員が接続せず、各自の`.local`に保存する。秘密情報とDBファイルをGit共有しない。

## 分担

| 担当 | 所有範囲 | 依存する契約 | 完了確認 |
|---|---|---|---|
| A：地図・基盤・統合 | features/map, recording, fixtures、appの組立て、DBアダプター | TrackPoint, Place, MapRepository | 位置再生→保存→20m解放。再送で増えない |
| B：対話・個人・友人 | features/conversation, personal, friends、対話サービス | Message, Memory, PersonalAI、友人申請契約 | 会話が残る、訂正できる、相手だけが承認できる |
| C：提案 | features/transfer、将来の経路アダプター | 別途固定するRouteProviderと好みの共有投影 | 未確認条件を満たした扱いにせず、共同経路を計算 |
| D：機能生成・修復 | features/extensions、将来の生成・実行アダプター | 別途固定するFeatureRunner, SourceAdapter | 独立検証後のみ有効化し、修復失敗時に旧版を維持 |

現時点ではC/Dの処理契約と共有投影の詳細は未確定。全機能の再現にはこれらを先に完成させる。

## 各担当へ渡す指示

全員：`docs/spec/implementation-status.md`、本書、共通契約を読む。他機能を直接importしない。
担当外ファイルが必要なら、必要な入出力を統合担当へ伝える。未実装の接続は画面で未接続と表示する。

- A：「地図と位置記録を担当。20m判定と軌跡の分断規則をdomainへ置く。実建物高さの欠落を補造しない。全機能の空パネルを最初に接続する。」
- B：「会話の原文をAI呼出し前に保存。AI失敗は待機、再試行で二重保存しない。本人の訂正を優先。友人追加だけでは非公開記憶を公開しない。」
- C：「友人の目線・自分向け・二人向けの入力と出力を分離。歩行経路の取得失敗に直線を代用しない。外部登録・費用は具体案で確認する。」
- D：「生成コードとホストを隔離。生成者が期待値を書き換えて合格しない検証契約にする。Docker未稼働なら未接続とし、隔離なしで実行しない。」

## 4時間＋1時間の進め方（目標）

1. 0:00–0:20 共通型・起動・空パネルを全員へ配布し、同じコミットから担当ブランチを作る。
2. 0:20–1:00 各機能の最小入出力を実装し、仮データで一回目の統合。
3. 1:00–2:00 保存・AI・経路・コード実行を接続。共有契約の変更は統合担当が一本化。
4. 2:00–3:00 成功経路と主な失敗経路を統合し、通しデモ。
5. 3:00–4:00 未完了を解消して機能を固定。互換性・端末確認。
6. 4:00–5:00 不具合調整・デモ練習。新しい仕様を増やさない。

## 統合条件

担当ブランチごとに`pnpm check`を通す。PRには実装範囲、契約変更、実接続か仮データかを記載。
統合順序は共通契約→保存→地図・記録→対話・訂正→友人共有・比較→提案→生成・修復。
各統合で`pnpm build`、該当する通しテストを実施。共通契約を変えたら依存担当の型検証も通す。

## 再現の合格条件

同じ内部構成・入力契約・保存規則・画面の流れを持ち、受入テストを満たすこと。
LLM応答文やソースコードの文字列一致は要求しない。根拠、訂正の優先、エラーからの回復で比較する。
完成後に別の空リポジトリからリハーサルし、実測時間と追加説明が必要だった箇所を本書へ追記する。
