# 空リポジトリから完成品を作るリハーサル

2026-09-09。今回のユーザー指示に基づく運用方針。今回は二人のCodexで、空のリポジトリへ仕様・開発用hooks・Issueを移し、チーム開発で完成品を作る。UI案は別セッションで作成中。本書は準備と改善の運用を定めるもので、準備完了を報告するものではない。

## 目的と正本

完成品を実際に操作し、仕様の不足、見た目や操作への要望、隠れた依存関係、Issueの書き方の問題を発見する。その知見を仕様・契約・タスク・開発環境へ反映し、本番では追加説明や同じ問題の再調査をせずに開発できる状態を作る。

リハーサル開始時にはStage2 v2.1の157要件と114タスクを初期基準とした。配布物はGitの保存コミット `5abdf93` に残し、現在の入口は[文書一覧](../README.md)とする。以下のv2.1に関する記述は開始時点の経緯であり、現在の取得条件は本番計画で確認する。変更理由と対応関係を残して改訂する。既存アプリのコードを移植して完成扱いにしない。仕様内の参照実装をどこまで持ち込むかは資産一覧に明記する。

2026-09-10の指定により、本番の要件・改訂計画の正本はOpenAICompetitionとする。[本番実装計画](../production-plan/v2/README.md)へリハーサルの学びを戻し、リハーサル側は実行台帳・受入履歴と配布用の写しを管理する。ZIPは配布時点のスナップショットとし、二つのリポジトリで計画を独立改訂しない。古い4人固定担当・時間割の手順を開始指示に混ぜない。

## 開始前にリポジトリが備えるもの

これらを人間向けの宿題にせず、準備IssueとしてCodexが整備する。接続先の指定、本人の認証操作、利用体験に関する判断など、本人にしかできない入力だけを依頼する。秘密値は文書やIssueに記録しない。

| 準備ID | 成果物 | 完了の確認 |
|---|---|---|
| PREP-001 | 空リポジトリへの仕様・契約・ツール移植、資産一覧、正本の優先順位 | 全員が同じ開始コミットを取得でき、既存アプリ・DB・秘密値を含まない。参照コードの持込み範囲が分かる |
| PREP-002 | バージョン固定、依存導入、起動・検査コマンド、環境変数例、接続状況の確認手順 | 新規cloneで再現可能。未実装の起動コマンドを成功扱いしない。実装後に新規cloneでも起動を確認する |
| PREP-003 | v2.1のタスク取得と整合するhooks、導入・確認・復旧手順 | 二つのclone/worktreeで通常作業を許可し、同一タスクの二重取得と取得範囲外の変更を検出。台帳更新を誤って拒否しない |
| PREP-004 | GitHub Issue、Task IDとの対応、共有台帳、担当取得・提出・統合手順 | 再実行でIssueが重複せず、二人が別タスクを取得可能。通常merge後にdoneとロック解放を確認 |
| PREP-005 | 実装中の仕様・依存・Issue変更手順とツール | 作業中・提出済みの状態を壊さず計画と台帳を更新できる。循環依存・削除済みIDを検出し、失敗時は旧状態を保持 |
| PREP-006 | UI受領先、画面ID、共通スタイルとコンポーネント、状態・操作の対応表 | 別セッションの成果物を同じ版で参照できる。未確定UIに依存しない作業は先に取得できる |
| PREP-007 | 地域・サンプル記録・外部データの出典と取得手順、Codex/地図/経路の接続確認 | 表示用サンプルと実接続を区別し、再現に必要な設定を文書から辿れる。追加課金を自動で有効にしない |
| PREP-008 | 下記の発見記録、変更テンプレート、完成品の通し確認手順 | 一件の発見から仕様・Issue修正まで追跡でき、次の新規cloneで修正の有効性を確認できる |

PREPは実装開始のための作業であり、製品要件を増やした数には含めない。全PREPの終了を全機能の開始条件にせず、実際に必要な前提だけを依存として登録する。

## 二人の進め方

一つのタスクに一つのCodexと専用branch/worktreeを使う。担当範囲を二人に恒久分割せず、READYの優先タスクを取得する。共通ファイルの変更は必要なpathをまとめて取得する。レビューや統合も担当者の固定待ちにしない。統合担当が自分の作業に必要なロックを持つことも確認する。

moduleの単体確認、API/DBとの接続、実AIの接続、利用者の操作による完了を区別する。対応する統合タスクの受入が通るまで、画面が存在するだけで製品機能を完了にしない。完成目標は全体の利用体験であり、着手順の優先度を理由に残りを暗黙に対象外にしない。

## 発見を仕様へ戻す

発見ごとに `docs/learnings/LRN-番号.md` を作る。下のテンプレートを使い、観測事実、要望、原因の仮説を分ける。スクリーンショットや実行結果は対象コミットと結び付け、個人データを除く。

1. 実装者が発見を記録し、影響する要件ID・Task ID・ファイルを特定する。
2. 誤記、再現可能な不具合、隠れた依存、Issueの不足は、既存の意図を保って修正する。利用体験や対象範囲を変える案は、具体的な画面・操作と変更理由を示してユーザーに判断を求める。依存しない作業は継続する。
3. 仕様、必要な契約、TASK_GRAPH、生成Issue本文、受入例を同じ変更として揃える。GitHub Issueだけに決定を残さない。
4. 実行中台帳のclaim・token・提出コミットを保持して変更を反映する。取得済みタスクへ新しい依存や編集範囲が影響する場合は、その作業を調整してから反映する。board再初期化で解決しない。
5. 新しい操作例・反例で確認し、発見記録に修正コミットと確認結果を追記する。未解決なら未解決のまま残す。

Issueの本文には、目的、利用者の操作と保存結果、対象要件、入出力、編集範囲、着手依存、接続依存、具体的な受入例、未接続の扱いを含める。大きすぎるIssueは安定IDを残して子タスクに分け、旧Issueから後継へリンクする。依存を追加するときは「何が欠けていて着手できないか」を書き、接続時だけ必要ならconnect_afterに置く。

## hooks移植で判明している差分

既存 `codex-team-workspace` はCODEX_OWNER・担当者名付きIssue/branch・GitHub assigneeを軸にする。v2.1はTask ID・原子的claim・pathロック・共有Git参照を軸にする。既存hooksの丸ごとコピーは二つの異なる取得ルールを重ねるため、PREP-003で適合させる。

またv2.1のtaskctlは、実行途中のgraph更新を自動化していない。依存発見を繰り返す今回のリハーサルでは、PREP-005で状態を保つ更新を具体化する。新規Issue登録だけで既存Issue本文まで同期されると仮定しない。
