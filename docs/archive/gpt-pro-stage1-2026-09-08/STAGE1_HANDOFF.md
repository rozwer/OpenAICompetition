## 1. 結論：何で勝つ案にするか

### 1.1 製品の一文

> **育てる地図は、「どこへ行ったか」ではなく「そこで何を得て、なぜ選んだか」が育ち、その理解を他の人・他の街でも使える地図。**

利用者向けには「毎日が、自分だけの街になる」。審査員向けには「本人が訂正できる体験の記録を、地図の成長・条件付きの自己理解・体験の移し替え・Codexによる機能拡張で共有する」と説明する。

日常の入口は、講義・仕事帰りの20〜30分の寄り道、よく行く場所の記録、友人からの実用的な体験である。これは検証を始める入口であって、旅行、バイク、聖地巡礼、防災を削るための対象者限定ではない。友人がいなくても自分の記録と公開体験から価値が出る。

### 1.2 現案の強さと弱点

強さは、地図を育てる感覚的な楽しさと、用途・理由・他者の視点という情報の深さが同居していること。自分の建物が姿を変えるだけでなく、その理由が「次にどこへ行くか」を変えると、見た目と実用性が接続する。

弱点は、現状の説明では「3D地図」「日記」「おすすめ」「性格診断」「友人SNS」「プラグイン」が別々のサービスに見えやすいこと、そして診断・移し替えの正しさを文章の自然さで済ませる余地があること。

Googleの公式発表には会話型の場所探しとImmersive Navigationがあり、Fog of Worldには探索記録、Polarstepsには旅行の計画・記録・共有がある[W02, W15, W16]。「AIがおすすめ」「訪問で地図が変化」「3D」「記録を共有」だけを未踏の独自性として売り出すべきではない。各サービスの全機能を網羅比較したわけではなく、本案の世界初を主張しない。

差別化の中心は次の連続動作とする。

**本人の一言 → 根拠付きの用途・理由 → 建物の変化 → 条件付き仮説 → 本人の訂正 → 同じ候補に対する提案の変化 → 他者・他都市の体験 → 実際の感想で更新。**

これを動作と記録で証明することが、汎用チャットへ長いプロンプトを与えるだけのデモとの差になる。個々の手法の発明を主張するのではなく、実際の制約、版、権限、検証を接続したシステムとして価値を示す。

### 1.3 4タブが共有するもの

| タブ | 利用者に見える価値 | 共通する体験データの使い方 |
|---|---|---|
| 地図を育てる | 自分の経験が街の姿と次の行き先になる | 確定訪問は成長、確認した用途は造形、現在の希望は候補選びに使う |
| みんなで育てる | 同じ場所の違う使い方、違う街の似た体験を発見する | 許可された用途・理由・順序を比較し、体験レシピとして移す |
| アプリを育てる | 必要になった判断・表示を追加する | 同じ根拠・権限・経路の契約の上へプラグインを追加する |
| 自分を知る | 自分が何を優先するかを、根拠と反例から知る | 記録を診断の材料にし、訂正を全体へ戻す |

AIチャットを4つ作るのではなく、記録と訂正は一度行えば各画面へ反映される。一方、用途の変更・訪問の変更・好みの変更は別の操作であり、訂正が無関係な情報まで壊してはならない。

## 2. 「占いではない診断」の具体案

### 2.1 診断を撤去せず、出力する命題を変える

「あなたは内向型」「冒険家タイプ」ではなく、**「平日の帰宅前、一人で時間が少ない場面では、遠い新規店より、寄り道の短さと落ち着けることを優先しやすい」**という条件付きの命題を扱う。

画面の名称は「街との付き合い方」。補足として「状況別の行動パーソナリティ」を使える。これは新しい心理検査が科学的に妥当と証明されたという意味ではない。既存研究には、性格に関連する行動の状況依存性や個人内変動を扱うものがあるが、それだけで位置ログから性格を診断できることにはならない[W10]。

画面には、本人が言ったこと、観測できたこと、モデルの仮説、反例・別の説明、次に確かめたいことを分けて示す。2体験から仮説を作ることはできても、2体験で傾向が検証済みとは言わない。

### 2.2 学習するのは「選べたとき、何を優先したか」

通学先に100回行ったことは、その場所を100回自由に選んだという意味ではない。未訪問の店も、知らなかった・閉店していた・高かった・その日は時間がなかった可能性がある。推薦ログの選択バイアスは既存研究でも問題とされている[W12]。

保存する単位は、状況、表示した候補集合、各候補の実行可能条件、選択・見送り、本人の理由、体験後に目的に合ったかである。出せなかった候補や見ていない候補を「嫌い」として学習しない。

初期実装は、巨大な独自学習モデルではなく、少数の属性と状況との交互作用を持つ正則化二者選択モデルを推奨する。数式は実装方針の例であり、最終のモデル・推定法はStage2でテストして定める。

\[
P(a\succ b\mid u,c)=\sigma\{w_u^\top[\phi(a,c)-\phi(b,c)]\}
\]

`c`は平日/休日・時間・同行者・予定・明示された現在の希望等、`φ`は移動増分・追加費用・既知/新規・本人が確認した環境などである。利用可能な選択肢だけが比較対象となる。静けさ等の根拠がない属性に想像の値を入れない。

初期の事前分布や正則化は推定を安定させるための仮定であり、精度保証ではない。申告から始め、二者選択と結果から更新し、小標本では不確実性を残す。場面ごとに変わる状態を、長期的な傾向に全部吸収させない。冷開始は明示条件に基づく推薦で成立させ、学習データが貯まるまで利用をロックしない。

文脈に応じて選択し結果から更新する推薦はcontextual bandit研究と接続できる[W11]。ただし、本製品で何を報酬にするかは独自の設計であり、クリック率や移動距離を最大化するのではなく「本人がその場面で望んだ体験への適合」を優先する。探索のために危険・費用・同意の制約を緩めない。

### 2.3 診断が機能していると見せる操作

例：AIが「静かさを優先している可能性」を提案する。本人は「この日は時間がなかっただけ」と訂正する。

その結果、当該体験を静かさの支持証拠から外し、候補集合を固定した次の推薦の順位と理由を再計算する。既に本人が確認した訪問や「勉強した」という用途は変えない。別途用途も訂正した場合だけ、該当建物の造形を更新する。

これにより「自分の説明が修正できる」だけでなく「誤った理解が次の行動へ残らない」ことを示せる。推薦候補自体を同時に入れ替えると訂正の効果が分からないため、デモでは同じ候補集合を用いる。

### 2.4 質問と小さな検証

毎回長い質問票を出さず、対立する説明を分ける一問を出す。例えば「同じくらいの距離なら、静かな場所と、新しい発見がありそうな場所のどちらに寄りたい？」。どちらも行ける条件でなければ有効な比較とはしない。

情報利得を用いる質問選択は追加する価値があるが、実装の初手は明確な競合仮説に対するルール選択でよい。後に同じ契約の中で事後分布に基づく選択へ進める。質問の少なさ、辞退可能性、機微性を一緒に評価する。

希望者が次回の別場面で試し、その結果を仮説へ戻す。「当たっている気がする」という自己申告だけを精度と呼ばず、別場面での選択・結果・外れた事例を記録する。これは自己理解の補助であって、臨床的・因果的な効果の証明ではない。

## 3. 体験の移し替えとArea2Vec/OpenUAS

### 3.1 体験レシピ

「この店と似た店を探す」ではなく、体験を次の構造で持つ。

| 要素 | 説明例（架空の体験） |
|---|---|
| 目的 | 帰宅前に気分を切り替える |
| 役割の列 | 本屋で新しい話題に触れる → 視界が開けた場所で一息つく |
| 順序・遷移 | 刺激を受け取ったあと、余白のある場所へ出る |
| 理由 | 本に囲まれる感じ／空が見えること |
| 必須条件 | 到着期限、追加費用、歩行上限、座席が必要ならその確認 |
| 変更可能なもの | 店名、建物、移動手段の一部 |
| 移せないもの | そのときの友人との会話、個人的な思い出 |

AIはこの構造の抽出と説明を担う。候補取得、順序、時間・料金・道路・営業条件は独立に検証する。これを「体験コンパイラ」と呼んでもよいが、検証できるのは構造・データ・制約であり、主観的に同じ気持ちになることを形式的に証明するものではない。

「相手の体験に忠実」「自分の条件に合う」を別軸にして比較し、保存した・変えた・再現できない・まだ不明を明細にする。見かけだけの再現率ではなく、利用者が変更内容を選べることに価値を置く。

### 3.2 OpenUASを置くのは、地域候補の取得部分

OpenUASは都市の滞在に基づく地域利用の埋込みを公開しており、異都市比較のためのアンカーを持つ。公開説明の対象は東京、大阪、名古屋、札幌、福岡、仙台、広島、京都の8都市である[W03, W04]。

採用案は、元体験が持つ地域利用の特徴から、別都市で類似する地域を候補に含め、その地域内で実際の施設・用途・現在条件を調べることである。カテゴリ検索、地域情報からの検索、UAS類似検索を併用し、UASが適さない体験や都市でも本体は同じ処理で動く。

UASを入れるだけで推薦がよくなるとは言えない。比較可能なモデル版であることを確認し、UASなしとの候補取得比較を行う。地域取得の効果を見るため、この評価では同じ候補集合に固定せず、同じ探索対象・検索予算を用いる。診断訂正の評価で候補を固定することとは目的が違う。

### 3.3 やってはいけない結び付け

地域ベクトルから「内向的な人の街」「この店は静か」「ここは今空いている」と断定しない。意味を学習していない潜在次元に、静けさ等の名前を勝手に付けない。個人の選好モデル、文章埋込み、UASベクトルを同じ空間とみなして内積しない。

公開データには過去の期間が使われ、50mメッシュの一部には250mから補完したものがある。`is_complemented`と元の解像度・時期を保持する[W03, W04]。席、騒音、店の営業、今日の混雑、災害時の通行は別の出典か本人の確認を必要とする。

### 3.4 地域と権利の判断

最初に実際の収録と経路を確認する比較地域は、既存試作を生かす名古屋と、公式都市一覧にある東京を推奨する。横浜は開催地・既存地図の候補として保持するが、公開の8都市名一覧だけから横浜の厳密なメッシュ収録有無を断定しない。横浜・箱根の体験にもUASがあると偽らず、実収録が確認できた範囲で有効化する。

公開説明はArea2Vecに関する特許と商用時の連絡先を案内している[W03]。オープンデータという名前から商用・再配布無制限と判断しない。コンペ利用、切出しデータの同梱、モデル・コード、将来商用を分けて確認する。

### 3.5 3D人流研究とのもう一つの接点

同じ建物の地下の交流場所と上層階の作業場所を別の場所として扱う「同じ建物、違う意味」は、元要件の階・入口の区別を生かす自然な追加体験である。2Dの見栄えを3Dへ変えるだけでなく、同じ平面位置にある異なる用途を混ぜない価値になる。

高度付きの研究資産を使う場合も、既存モデルが本ZIPにある・自由に配布できる・階を正確に識別できるとは仮定しない。高さ帯と階番号を区別し、本人確認やデータ出典と併用する。PLATEAU全面導入を再度依存条件にする提案ではない。

| RV17／P2 | 新規研究案 | UASの任意ベクトル演算や心理型の発明を急ぐと検証不能 | 保留推奨：必要な論文・モデル・適用条件が確認できてから追加 | TRF-008, SELF-014 |

## 5. 実現可能性：何が既知で、何が未検証か

**技術的な経路はあるが、現時点で全機能の当日完成を保証できる状態ではない。** 特に外部契約・データ範囲・描画差替え・任意コード隔離は、人数を増やしたり最後に頑張ったりするだけでは解決しない。これらをG0へ出し、他の実装と並行して潰す。

| 対象 | 成立の見通し | 外部確認/未確認 | 先に通す検査 |
|---|---|---|---|
| 根拠付き体験、訂正、比較 | 既存設計に保存・版の骨格があり、通常のアプリ実装として具体化可能 | 本ZIPにDB/API実装なし | 1体験の保存→訂正→派生失効が再現する |
| 条件付きプロファイル | 少数属性の推定と質問選択で始められる | 対象者での有効性・学習データ未検証 | 合成の明確な選択差＋未使用場面の評価 |
| 象徴建物への置換 | Mapbox公式にStandardの建物をclipで消し独自モデルへ替える例がある[W05] | 実験的機能。密集街区・複合建物・対象版での確実性は未検証 | 1棟置換、隣棟保持、原形復帰、30fps目標の実測 |
| OpenUAS候補取得 | 公開データ・モデルと異都市比較の設計がある[W03–04] | 正確な地域メッシュ、モデル整合、権利、推薦改善は未検証 | 対象2地域のデータ確認と同予算の候補比較 |
| 徒歩経路 | Mapbox等に歩行経路APIがある[W07]。旧設計ではopenrouteserviceを候補とした | 最終プロバイダー・契約・地域の歩道/階段等は未選定 | 実道路接続、到達不能、逸脱、階段条件 |
| 交通・定期運賃 | 駅すぱあととNAVITIMEには定期区間を考慮する資料がある[W08–09] | 駅すぱあとの当該定期控除は鉄道のみ。バス含む全券種や契約は未確認 | 対象券種ごとの小さな実リクエストと期待値照合 |
| ストアと3プラグイン | manifest・権限・導入版を共通化できる | 各プラグイン用の実データ・更新・CORS・利用権は別問題 | 3種それぞれの入力→出力を共通契約で通す |
| 新規コード実行 | Codexからの生成・イベント・承認は公式に扱える[W13–14] | Codexのsandboxと配布プラグインのsandboxは別物。後者は未実装 | 無限ループ、無断通信、親DOM、過大出力の負例 |
| 防災・バイク | 根拠と不明を保持した情報提示は設計可能 | 災害中の安全・車種別全道路通行を保証できるデータは未確保 | データがない場合に危険な断定をしないこと |
| 端末背景記録 | 原案どおり実機段階で既存SDK接続を検討 | Safariデモは背景測位・省電力・ストア審査を証明しない | 実機の権限・復帰・電池・継続記録試験はG6 |

Mapbox Directionsだけで日本の鉄道・バス時刻表と定期運賃まで作る想定は置かない[W07]。ルーティング層を歩行・公共交通・車種別制約へ分け、プロバイダーごとの対応範囲を可視化する。「無料ルート」や「走れる道」という表現は、確認できた条件内に限る。

外部から静けさや座席が確認できない施設について、LLMに調べたふりをさせない。本人の過去体験、公式情報、利用可能な現地データ等のどれが根拠かを示す。過去体験を現在保証に読み替えない。

## 6. 用語と横断する不変条件

| 用語 | この製品での意味 |
|---|---|
| 観測 | センサーや入力元が返した位置・時刻・精度等。訪問の証明ではない |
| 訪問候補 | 立寄った可能性。複数施設・階不明・否定を持てる |
| 確定訪問 | 本人の明示確認を根拠とする訪問。再送で増えない |
| 体験 | いつ・どこで・誰と・何を・なぜ・どうだったか。GPSなしでも成立する |
| 用途 | その人が何のためにその場所を使ったか。施設カテゴリとは別 |
| 理由 | なぜその場所や過ごし方を選んだか。用途とは別 |
| 状況 | 時間、同行者、目的、制約、本人が明示した現在の希望等 |
| 仮説 | AI・モデルが提案する説明。本人の発言でも確定事実でもない |
| 行動プロファイル | 状況に応じた優先・選択の記述。固定性格型や臨床診断ではない |
| レンズ | 誰の許可された用途・理由・視点を重ねて見るか。所有者は変わらない |
| 体験レシピ | 目的、役割、順序と遷移、理由、制約、変更可能部分、移せない記憶 |
| 忠実さ | 元の体験で大切だった構造をどれだけ保持できたかという評価軸 |
| 自分適合 | 試す本人の現在の条件・希望にどれだけ合うかという別の評価軸 |
| 根拠 | 原文・記録・公開資料・版・適用範囲・権限を追える参照 |
| プラグイン | 宣言された入力・権限・出力・検証条件に従う追加機能。私有ログそのものではない |

数値の正確さ、出典の信頼性、本人の納得、条件の充足、統計的な確かさは別々である。不明を0・否定・無料・安全と置き換えない。本人訂正と共有取消は、新しい推論や再生で消えない。記録の事実とその解釈を分け、レンズを切り替えても書き換えない。

## 7. 改善済み要件の全文

各IDはStage2で画面・データ・API・ジョブ・テストへ追跡する。IDは削除・再採番せず、変更時は履歴を残す。

位置付けの「既存要件」は最新資料に既にあるもの。「既存設計案を継承」は従来の詳細案で、承認済みの技術選定とは限らない。「今回の追加・変更提案」は本レビューの推奨であり、ユーザー承認済みではない。

工程G0〜G5は今回の全機能の実装・検証、G6は従来の実機/配布や明示された将来項目。必須と望ましいの違いは保持する。今回追加案の必須は「この推奨案を採用する場合の完成条件」を指す。

### CORE 要件

#### CORE-001 製品の目的

**位置付け：今回の追加・変更提案／重要度：必須／工程：G1／元参照：CONTEXT／R全体**

場所の収集だけでなく、状況・用途・理由・結果を本人が育て、その理解を自分の地図、他者との比較、別都市の行動、機能追加に再利用できる製品とする。全4タブを同じ体験と根拠の参照でつなぐ。

**受入条件：** 同一の体験IDから、建物の表示・条件付きプロファイル・比較・移し替え・感想へ追跡できる。

#### CORE-002 初回から一人で成立

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R地図§1／R一緒§1／R自己§1–2**

位置履歴・友人・長期学習がなくても、場所の選択と一言から体験を保存できる。公開情報の閲覧、通常の経路案内も使える。個人化の不足を架空の履歴で埋めない。

**受入条件：** 履歴なし・友人なし・位置権限なしのアカウントで、体験保存と公開体験検索が完了する。

#### CORE-003 4つの成長を分離

**位置付け：今回の追加・変更提案／重要度：必須／工程：G1／元参照：R地図§2／R自己§3–4／Rアプリ**

訪問による造形の成長、本人の説明による意味の成長、検証された予測の成長、導入機能の成長を別の状態として扱う。活動量の多さを人間としての成長に換算しない。

**受入条件：** 訪問数だけ増えても好き・性格・診断確信度が自動上昇しない。

#### CORE-004 重要度と実装順の分離

**位置付け：既存要件／重要度：必須／工程：G0／元参照：01_PROMPT／今回ユーザー指示**

既存の必須機能を削らずG0〜G5の完成対象とする。望ましい機能と従来から将来だった実機配布等を区別する。工程の後ろに置くことを機能撤回や成功扱いの緩和に使わない。

**受入条件：** 全既存要件にID・工程・受入条件が対応し、未完了項目は未完了のまま確認できる。

#### CORE-005 事実と実演の誠実性

**位置付け：既存要件／重要度：必須／工程：G0／元参照：S実装§1／Sデータ§9–10／A52・55**

本人申告・実測・公開情報・合成入力・AI仮説を区別し、実API・入力再生・保存済み結果も別に記録する。保存済み映像や計算結果を今回の生成・実測成功と説明しない。

**受入条件：** 表示レイヤーやジョブごとに入力由来と実行方式を確認できる。


### NAV 要件

#### NAV-001 4タブの順序

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R画面§4タブ**

下部タブは「地図を育てる」「みんなで育てる」「アプリを育てる」「自分を知る」の順序とする。ホームとAIを独立した第5・第6タブにしない。

**受入条件：** 全主要画面で順序が一致し、主要機能が4タブ内から到達できる。

#### NAV-002 起動とホーム

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R画面§起動**

ホームの起動時表示は設定で切替え、既定ONとする。OFFなら自分レンズ・2Dの地図へ入る。ホームには今日の再開先、記録、提案を置き、強制的な診断を入口にしない。

**受入条件：** ON/OFFを保存し、再起動後も意図した入口と既定表示になる。

#### NAV-003 レンズと次元の独立

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§1／付録モード**

自分・友人・ペルソナのレンズと、2D/3Dの次元を独立して切り替える。友人の情報は共有許可内に限り、架空ペルソナは実人物の発言と区別する。

**受入条件：** 自分2D→友人2D→友人3D→自分3Dの全遷移で個人記録が変わらない。

#### NAV-004 意図した3D切替

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図付録モード**

2Dから明示的に3Dへ移り、場所タップや単なるズームで勝手に3D化しない。3Dでは人物中心の表現を使い、2Dへ戻ると以前の範囲を復元する。

**受入条件：** 施設を選んでも2Dのまま詳細が開き、戻った際に元の2Dカメラが復元される。

#### NAV-005 タブをまたぐ文脈

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R画面§引継ぎ／S実装§4**

場所・体験・比較・経路・人物・期間・レンズ・カメラ・入力下書きを引き継ぐ。タブ切替やレンズ変更で進行中の案内を暗黙に置換しない。

**受入条件：** 各タブ往復で対象が一致し、案内停止・経路置換は明示操作でのみ起こる。

#### NAV-006 AIの参照範囲

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R画面§AI**

AIは現在の対象と参照範囲を表示し、変更・解除できる。送信時に対象と版を固定し、送信後に別の場所へ移っても回答を新しい場所へ誤適用しない。

**受入条件：** 場所Aへ送信後Bへ移動してもAに保存され、参照解除後は私有履歴を自動追加しない。

#### NAV-007 AIなしの操作

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R画面§AI／R地図§1・4**

訪問記録、用途の手入力、写真、通常の検索・経路案内、共有の管理はAI会話なしで実行できる。

**受入条件：** AI未接続・応答失敗時にも非AI操作と入力保存が完了する。

#### NAV-008 画面サイズと状態

**位置付け：既存設計案を継承／重要度：必須／工程：G5／元参照：S実装§4・15／A53–54**

390×844 CSS pxを基準に、半面・全画面パネル、入力時のキーボード回避、大画面の左右比較を設計する。色だけで不明・失敗を表さず、動きを減らす設定を提供する。

**受入条件：** iOS Simulator Safariで入力・スクロール・戻る・選択が通り、色を見なくても状態が読める。

#### NAV-009 設定と通知

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R画面／R地図§3／R自己§7**

ホーム、位置記録、共有、クエスト、動き、導入済み機能の設定は「自分を知る」からも管理する。質問や探索の通知を停止しても通常利用を妨げない。

**受入条件：** 設定への到達が一貫し、OFFの通知が再開・別タブで復活しない。


### REC 要件

#### REC-001 観測・候補・訪問・体験

**位置付け：既存要件／重要度：必須／工程：G1／元参照：CONTEXT／R地図§1／R自己§1**

位置観測と訪問候補と確定訪問と本人の体験を分離する。写真・経路の通過・検索閲覧だけで訪問を確定しない。本人申告の体験はGPSなしでも持てる。

**受入条件：** 駅前を通過したログで店の訪問数が増えず、手動の過去体験は記録できる。

#### REC-002 今ここ・過去の手動登録

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R地図§1／R自己§1**

「今ここにいる」、地図タップ、候補選択、施設検索、短い自然文で登録・修正する。今の位置と過去日の体験を混同しない。

**受入条件：** 現在地点を動かさずに別日の場所を編集でき、候補外施設への修正も可能。

#### REC-003 欠測と概略の保持

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R地図§1／R自己§1／A04**

不明区間、精度不良、日時や滞在時間の不明を保持する。「この辺」「昼頃」を偽の秒精度や正確な道路線へ変換しない。分からない・後でを許す。

**受入条件：** 欠測区間は切れたまま示し、入力がない一日全体の軌跡を描かない。

#### REC-004 候補の確認・拒否・訂正

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R地図§1／A05–06**

位置から複数の候補を作れても本人の明示根拠で確定する。施設・日時・階を訂正でき、却下を保持する。短時間訪問の手動追加も可能とする。

**受入条件：** 同一建物内の候補が複数なら自動確定せず、却下後の再生で同じ訪問が復活しない。

#### REC-005 一度だけ保存

**位置付け：既存設計案を継承／重要度：必須／工程：G1／元参照：S実装§5／A02–03**

入力元と元記録IDで観測の重複を防ぎ、受信順ではなく観測時刻で構成する。手動登録と観測由来候補が重複した場合は本人確認または明確な同一性で統合する。

**受入条件：** 同じ入力の再送で観測数・訪問数・造形段階が増えない。

#### REC-006 用途と理由と条件

**位置付け：既存要件／重要度：必須／工程：G1／元参照：CONTEXT／R自己§2**

施設種別、何をしたかという用途、なぜそこで行ったかという理由、時間・同行者・目的・移動制約を別に保存する。本人の原文を残す。

**受入条件：** カフェの「勉強」と「友人との会話」が共存し、カテゴリだけで同一用途にされない。

#### REC-007 確認は原則1問

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§1／R自己§2／A10**

記録後の確認は原則1問で、回答なしでも保存を完了する。回答済み・後で・飛ばすを保持し、同じ根拠だけでは聞き直さない。

**受入条件：** 一言保存後に画面を離れても記録が残り、再入場で同じ質問を強制しない。

#### REC-008 原文とAIの分離

**位置付け：既存要件／重要度：必須／工程：G1／元参照：R自己§2／A08・12**

原文を先に保存し、AI抽出は発言内の説明と追加仮説を区別する。AI出力のSchemaだけでなく、参照ID・公開可能項目・否定文・訂正範囲を検査する。

**受入条件：** 「好きではなく近かった」を好きと確定せず、途中出力や失敗時に関係を重複保存しない。

#### REC-009 写真の撮影・投稿

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§5／A07**

撮影、場所選択、文章、公開先確認、保存・投稿取消を用意する。位置不明は手動で補い、写真に写った施設への訪問を自動確定しない。

**受入条件：** 撮影取消で投稿がなく、共有前に公開される画像・文章・場所が確認できる。

#### REC-010 移動モード別の品質

**位置付け：今回の追加・変更提案／重要度：必須／工程：G1／元参照：S実装§5の修正／R地図§4**

従来の12m/s等の分断値は歩行再生向け設計値として扱い、鉄道・バイクに一律適用しない。移動モード不明時は品質不明を保ち、道路への補正結果も観測そのものと分ける。

**受入条件：** 正当な列車ログを全破棄せず、徒歩の瞬間移動は分断でき、使用設定版が残る。

#### REC-011 記録の削除と復元範囲

**位置付け：今回の追加・変更提案／重要度：必須／工程：G1／元参照：R地図§6／R自己§7／S実装§13**

訪問・理由・写真を削除したら派生表示や学習材料から除き、再計算する。訂正履歴の保持と、本人による削除要求は別処理とし、永続履歴という理由で削除を無効化しない。

**受入条件：** 削除した体験が再推薦・検索・診断根拠に残らず、合法的保持が必要なものは別途明示する。


### MAP 要件

#### MAP-001 共通地図の実用性

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§1／付録技術**

Mapbox Standardを基本に道路・水域・主要施設・必要なラベル・現在精度・案内線を読めるようにする。固定街区制限は製品全域へ適用せず、必要な都市へ移動できる。

**受入条件：** 施設探しと案内で名称が読め、名古屋から別都市へ切り替えられる。

#### MAP-002 訪問で建物が立つ

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§2**

確定訪問によって訪問した建物が立ち上がる。背景を含む現実地図と経験の印を分離し、周囲の建物を訪問済みにしない。

**受入条件：** 確認前後で対象建物だけの状態が変わり、友人レンズの閲覧で自分の建物が育たない。

#### MAP-003 用途で建物自体を変形

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§2**

本人が確認した用途に応じて、学びは本、交流は吹き出し、休息は庭などの象徴的な建物へ置換する。屋根の小アイコン追加だけで本要件を完了としない。複数用途を保持し表示対象を選べる。

**受入条件：** 同じ建物に用途を変えて本体形状の変化を確認できる。

#### MAP-004 再訪の造形段階

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§2**

確定訪問数をもとに造形・装飾が段階的に育つ。5段階の参考は形状の参考であり、好きの強さとはしない。段階境界は可変設定とし、訂正や削除で再計算する。

**受入条件：** 用途修正だけでは訪問回数が消えず、重複入力でも段階が増えない。

#### MAP-005 好きと成長の語彙

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：R地図§2参考画像**

回数で「お気に入り」「特別な場所」を自動付与しない。回数由来の段階名は中立な造形名とし、お気に入りは本人の明示操作・説明に基づく独立属性にする。

**受入条件：** 通学・勤務先への頻回訪問だけで好きと表示されない。

#### MAP-006 現実形状への復帰

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§2／S実装§9／A13**

現実の形状・高さと、自分の象徴的な造形を別データとして切替える。象徴表現を実測高さと称さず、原形へ戻しても記録は失わない。

**受入条件：** 現実表示に戻ると出典の高さが復元し、記憶を消さずに象徴表現を解除できる。

#### MAP-007 高さ・階の根拠

**位置付け：既存設計案を継承／重要度：必須／工程：G3／元参照：S実装§9／A14–15**

出典のある高さを使い、不明なら未確認と表示する。地下・上層階の施設、訪問階、階形状、入口・階段・エレベーターの接続を別の根拠で持つ。階数×定数を実測高さとしない。

**受入条件：** 建物訪問だけ確認・階不明・入口だけ確認を区別し、接続不明の屋内経路を確定しない。

#### MAP-008 人物の現在地表現

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図付録現在地**

シンプルで中立的な人物を用いる。移動が確認できる間だけ歩き、停止時は待機する。測位ぶれで歩かず、向きが不明なら向きを捏造しない。初期の着せ替え選択は対象にしない。

**受入条件：** 停止入力で歩行ループが止まり、位置精度円と向き不明の状態が分かる。

#### MAP-009 地図と同じ3D座標

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：試作src/main.js／R地図付録**

人物・象徴建物・屋根表示の位置、縮尺、遮蔽を地図のカメラ座標と一致させる。独立DOMキャンバスの見た目だけを世界座標で動く実装と称さない。

**受入条件：** 回転・ピッチ変更・高低差・ズーム・端末倍率で位置ずれと不正な透過を検査する。

#### MAP-010 屋根上表示とLOD

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図付録技術**

アイコンは高さの根拠に従って屋根に置き、建物の代表点は複雑な形状でも建物外へ逸脱しない方法を選ぶ。選択リングや接続表示を備え、遠景では集約する。

**受入条件：** 凹形建物・複数棟・高さ不明・密集街区で誤配置や読めない重なりを確認する。

#### MAP-011 不足ランドマークの補完

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図付録補完**

PLATEAU全面導入へ戻さず、既存地図で不足する限定ランドマークのみ、権利と形状根拠を確認してBlenderの編集元とGLBを用意する。参考画像の権利は実装素材と別に確認する。

**受入条件：** 補完モデルの出典・編集元・変換手順があり、都市全体の手作業モデル化を依存条件にしない。

#### MAP-012 帰属と軽量化

**位置付け：今回の追加・変更提案／重要度：必須／工程：G0/G5／元参照：試作style.css／W06**

Mapboxロゴ・必要な帰属表示を隠すCSSを修正し、見やすい位置に配置する。描画のLODや遅延読込は使うが、記録の根拠を間引きで書き換えない。

**受入条件：** 通常表示とモバイル表示で帰属が読め、地図のフレーム計測が人物fpsと分離される。

#### MAP-013 建物詳細の他者意見

**位置付け：既存要件／重要度：望ましい／工程：G3／元参照：R地図§5**

建物・入居施設を区別して、許可された体験、他者の意見、原文・投稿時点を参照する。施設への感想を建物内の全施設の評価へ転用しない。

**受入条件：** 原文の対象施設と時期が読め、共有取消後には意見本文が表示されない。

#### MAP-014 立体的な場所の意味

**位置付け：今回の追加・変更提案／重要度：望ましい／工程：G3／元参照：S実装§9／本人の研究接続案**

同一建物の地下・地上・上層で異なる用途を比較できる体験を追加する。高度付き研究モデルを使う場合も建物×高度帯と階番号を同一視せず、権利・モデル・誤差を検証する。

**受入条件：** 同じ2D座標の異用途を区別でき、階推定が不確実なら本人が選択・保留できる。


### ROUTE 要件

#### ROUTE-001 自動クエスト

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§3**

AIへの質問を待たず、本人の目的・条件、定期区間、許可された友人の実訪問、新規性から候補を出す。理由、所要時間・距離、既知の追加費用、成立条件をカードに示す。

**受入条件：** 会話していない状態でも根拠付き候補が現れ、未知の費用は0円と表示されない。

#### ROUTE-002 押し付けないクエスト

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R地図§3**

保存・後で・拒否・停止を用意し、直ちに再提示しない。実際の訪問を確認して完了し、保存・クリック・近接だけで達成としない。

**受入条件：** 拒否・停止が再起動後も有効で、候補保存だけでは訪問数が増えない。

#### ROUTE-003 歩行案内

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R地図§4**

出発・目的地・経由地を指定し、開始、停止、曲がり案内、経路逸脱後の再検索を提供する。観測線・計算経路・比較線を区別する。

**受入条件：** 実経路結果で案内でき、API失敗時に直線を歩道案内として出さない。

#### ROUTE-004 公共交通案内

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R地図§4**

鉄道・バス・徒歩を組み合わせ、出発/到着指定、乗換、事業者、時刻、徒歩接続、運賃を実データで示す。最速と最安を区別する。

**受入条件：** 鉄道＋バス＋徒歩の検証ケースで時刻と運賃の取得元を確認できる。

#### ROUTE-005 定期券の登録

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R地図§3–4**

区間・事業者・経由・有効期間・対象券種を登録し、検索時に有効なものだけ適用する。名称だけの曖昧な定期を推測で確定しない。

**受入条件：** 経由違い・期限切れ・未対応券種が検出される。

#### ROUTE-006 追加運賃と定期区間

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R地図§3–4／W08–09**

通常運賃と当該定期適用後の追加運賃を分ける。区間内でも対象外事業者・経由・種別なら無料と断定しない。単純な運賃差引きで代用せず対応プロバイダーの契約を検証する。

**受入条件：** 区間内、区間外、連絡定期、経由違い、バス、期限切れ、未設定で期待した状態になる。

#### ROUTE-007 時間内・追加費用内の寄り道

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R地図§3**

定期区間内、追加費用なし、30分以内などの条件と最終目的地への到着を同時に満たす候補を探す。寄り道の移動増分と滞在時間を分けて足す。

**受入条件：** 移動5分＋滞在20分を5分の寄り道とは表示せず、帰宅の到着制約も守る。

#### ROUTE-008 共有情報の由来

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R地図§3／R一緒§1**

友人の過去の実訪問と保存・おすすめを区別し、現在位置と誤解させない。元情報の取消に応じてクエスト・経路説明を失効または再計算する。

**受入条件：** 過去の訪問を「いま友人がいる」と表さず、取消した理由が候補に残らない。

#### ROUTE-009 制約と不明値

**位置付け：既存要件／重要度：必須／工程：G1/G3／元参照：R地図§4／S実装§8**

必須条件は満たす・満たさない・不明を区別し、不明を満たしたことにしない。候補なしの場合も利用者に黙って階段や費用等の条件を緩めない。

**受入条件：** 必須の座席・通行可否・到着条件が不明なら成立済み経路へ混ぜず不足を返す。

#### ROUTE-010 データ寿命と再検索

**位置付け：今回の追加・変更提案／重要度：必須／工程：G3／元参照：R地図§6／S実装§12**

時刻表・運賃・運行・営業時間の版と更新時刻を保持し、保存した旅行案は実行前に必要な再検証を行う。リアルタイム情報のないAPIをライブ運行保証としない。

**受入条件：** 古い保存案を開くと再確認対象が分かり、閉店・運休等の取得失敗を空の正常結果にしない。


### SOC 要件

#### SOC-001 目的・場所から検索

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§1**

目的、場所、または両方から公開・共有体験を探す。友人やインフルエンサーは任意フィルターとし、友人ゼロでも使える。

**受入条件：** 「休憩」「この周辺」の単独・複合検索で利用可能な結果が出る。

#### SOC-002 友人の接続・解除

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§1**

本人が接続・解除できる。接続方法は招待コードを推奨仮定とし、友人になっただけで全履歴を共有しない。

**受入条件：** 接続直後は未指定の写真・原文・軌跡が見えず、解除後の範囲を確認できる。

#### SOC-003 項目別・相手別共有

**位置付け：既存要件／重要度：必須／工程：G1/G3／元参照：R一緒§1・6**

場所、経路、用途、理由、写真、原文、集約活動範囲を個別に選び、相手/公開範囲とプレビューを確認する。保存や作成を自動投稿としない。

**受入条件：** 用途だけ共有した場合、原文や精密位置を参照経由でも取得できない。

#### SOC-004 実用的な体験

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§1**

ラーメンの「にんにく多め」の注文、服を買う巡回ルート、インフルエンサーの散歩等を具体的なコツとして保存する。実訪問、感想、推奨、店の現在の事実を混ぜない。

**受入条件：** 注文の工夫・巡回順・出典・訪問日が閲覧でき、過去の感想を現在の営業時間としない。

#### SOC-005 ルートの作成・共有

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§1**

作者、テーマ、立寄り先、順序、コツ、時間の根拠、更新日を持つルートを作成・保存・編集・共有・取消できる。AI改変は原ルートの別版として示す。

**受入条件：** 作者の投稿時間と現在の再計算ETAが区別され、編集で作者の原文が上書きされない。

#### SOC-006 意味の比較類型

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§2**

同じカフェの勉強/会話、同じ駅の別ランチ、川辺/本屋の気分転換、同じ公園の休憩、見慣れた建物の新しい用途という全例を扱う。場所一致と用途・理由一致を分ける。

**受入条件：** 5つの例をそれぞれ根拠付きで表示し、施設カテゴリ一致だけで結論を作らない。

#### SOC-007 比較の条件

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§2**

場所・状況・用途を入口として、人物、期間、平休日、時間帯、同行者で絞る。不明な条件を指定条件に一致したことにしない。

**受入条件：** 同じ人でも平日/休日、一人/同行者ありで違う比較を保持できる。

#### SOC-008 左右と地図の対応

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§2／A17**

自分・相手・重ね合わせと左右のカードを連動させる。別都市はそれぞれの地図へ到達でき、意味の対応を都市間の移動経路線として描かない。

**受入条件：** カード選択で正しい側の地図が動き、名古屋と東京を歩行案内の線で結ばない。

#### SOC-009 根拠と対応の訂正

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§2／A19**

共通点・違い・本人の説明とAI対応案を表示し、合う/違うを訂正できる。同じ入力版だけでは却下した対応を再生しない。情報不足は共通点なしと区別する。

**受入条件：** 却下が再読込み後も残り、引用権限が消えた根拠を閲覧できない。

#### SOC-010 友人レンズからの行動

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§3**

比較から友人レンズで見る、そこへ行く、別の街で試すへつなぐ。実人物の共有視点と架空のペルソナ提案を明示する。

**受入条件：** 選んだ元体験・用途・理由が移し替え画面へ引き継がれる。

#### SOC-011 一緒のコース

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§4**

本人と同行者の希望を混ぜて消すのでなく、各人の希望と共通の必須条件を示し、例えば本屋と水辺の両方を含むコースを選ぶ。合意前の送信はしない。

**受入条件：** 片方の必須条件が満たせないと説明し、候補を選んだだけでは相手に送られない。

#### SOC-012 体験の持ち帰り

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§5**

試した人が自分の写真・用途・理由・感想を新たに保存する。元の作者の体験と自分の体験を分離し、共有返信には相手と項目の確認を置く。

**受入条件：** 自分の感想が次の自分の推薦に使われても作者の説明が変わらない。

#### SOC-013 体験で返信

**位置付け：今回の追加・変更提案／重要度：望ましい／工程：G3／元参照：R一緒§5の拡張**

体験レシピを試した結果を、維持できたもの・変えたもの・自分に合った点として返信する。位置や原文を公開しなくても返せる。人数やいいね数で正しさを確定しない。

**受入条件：** 受信者が共有許可された差分だけ読め、返信取消も反映される。

#### SOC-014 共有取消の表示

**位置付け：既存要件／重要度：必須／工程：G1/G3／元参照：R一緒§6／A21–23**

検索、比較、保存、クエスト、AI会話、実行中の生成を含め、取消済み情報をアプリ管理下で再利用しない。相手が新しく体験した記録は別扱いとする。

**受入条件：** 開いている画面と生成完了直前のケースでも失効版が公開されない。


### TRF 要件

#### TRF-001 体験レシピへの分解

**位置付け：今回の追加・変更提案／重要度：必須／工程：G3／元参照：R一緒§3／S実装§8**

元体験を目的、役割、順序、理由、必須条件、変更可能な要素、移せない記憶に分解し、本人が確認できる「体験レシピ」にする。抽出元と仮説を保存する。

**受入条件：** 「本屋→水辺」を店舗カテゴリの置換だけにせず、前後の意味と理由を編集できる。

#### TRF-002 遷移を含めた移し替え

**位置付け：今回の追加・変更提案／重要度：必須／工程：G3／元参照：Sデータ§6の拡張**

場所の役割だけでなく、例えば刺激を得る→視界の開けた場所で落ち着くという段階間の関係も候補に用いる。同じ施設を再訪する行程は別の役割ノードで表す。

**受入条件：** 立寄り先が同じでも順序を入れ替えると元体験の維持評価が変わる。

#### TRF-003 候補取得と検証の分離

**位置付け：既存設計案を継承／重要度：必須／工程：G3／元参照：S実装§8**

役割に合う候補を集めた後、地理・営業時間・費用・歩行/交通・必須条件を独立に検証する。LLMが文章を書けることを到達可能性の証明にしない。

**受入条件：** 候補の実在と経路を確認し、必須条件が欠けた候補を成立済みから除ける。

#### TRF-004 忠実さと自分適合

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§3／A28**

元の人の視点を保つ案と自分向けの案を切り替える。忠実さ、自分への適合、根拠充足率は別の値とし、重みは設計仮定として明示する。

**受入条件：** 同じ候補集合でモードを切り替えると理由と順位が説明可能に変わる。

#### TRF-005 移し替えの明細

**位置付け：今回の追加・変更提案／重要度：必須／工程：G3／元参照：R一緒§3の具体化**

維持した役割・条件、変更した場所・手段、再現できない記憶や人物、未確認情報を対照表示する。未校正の数値を「再現度87%」のような確率にしない。

**受入条件：** 選ばれた行程の全要素が元体験か本人の変更へ遡れ、不明が一覧で読める。

#### TRF-006 共同選択と不成立

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§3–4／A29–32**

目的地や時間が両立しなければ、何を変更すると成立するかを提案し、承認されるまで条件を変えない。思い出・友人関係・その日固有の気持ちの再現は保証しない。

**受入条件：** 条件なしで候補を捏造せず、変更前後を明示する。

#### TRF-007 OpenUASの役割

**位置付け：今回の追加・変更提案／重要度：必須／工程：G3／元参照：今回ユーザー希望／W03–04**

OpenUASを異都市で都市利用の似た地域を探す候補取得の事前情報として使う。施設カテゴリだけでは探しにくい地域の候補を広げ、最後は個別の用途・条件・現在データで検証する。

**受入条件：** 同じ評価コーパス・取得予算でOpenUASあり/なしの候補と適合を比較できる。

#### TRF-008 OpenUASの意味境界

**位置付け：今回の追加・変更提案／重要度：必須／工程：G0/G3／元参照：W03–04**

共通のアンカー整合性・版・対象時期・対象範囲を検証する。地域ベクトルを性格、店内の静けさ、リアルタイム混雑、災害危険度、個人の嗜好ベクトルと同一視しない。別々の埋込み空間を直接内積しない。

**受入条件：** メッシュ・時期・モデル版・補完フラグから根拠を示し、範囲外はUASなしと表示される。

#### TRF-009 補完メッシュと広域性

**位置付け：今回の追加・変更提案／重要度：必須／工程：G3／元参照：W03–04**

50mメッシュでも250m由来の補完は粗い根拠として扱う。地域の用途類似から個別店の席・騒音等を推定しない。単純カテゴリ検索からの候補も残して、UASが全候補を独占しない。

**受入条件：** 同じ250mから補完した複数メッシュを独立した高解像度証拠として数えない。

#### TRF-010 地域と利用権

**位置付け：今回の追加・変更提案／重要度：必須／工程：G0／元参照：W03–04／S実装§3**

主デモの比較は名古屋と東京を推奨し、実際のメッシュ収録を確認する。横浜・箱根は元の地域候補として保持するが、UAS収録を未確認のままあるとしない。配布・コンペ・商用の権利を分けて確認する。

**受入条件：** 地域manifestとライセンス記録があり、未収録地域のベクトルが捏造されない。

#### TRF-011 体験後の更新

**位置付け：既存要件／重要度：必須／工程：G3／元参照：R一緒§5／A33**

選択・訪問・見送り・感想を結び、見送り理由を好みと機械的に同一視しない。新しい本人の説明で次の候補や条件を更新する。

**受入条件：** 行けなかった理由が時間不足なら店嫌いへ学習せず、条件を変えると候補に戻れる。


### SELF 要件

#### SELF-001 今日と過去の振り返り

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R自己§1**

今日の時系列・地図を見て過去日へ移動できる。候補・確定・不明・記録なしを区別し、見えていない移動を捏造しない。

**受入条件：** 欠測のある日、記録ゼロの日、本人申告だけの日を区別して閲覧できる。

#### SELF-002 用途と理由の発見

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R自己§2**

川辺と本屋がともに気分転換でも、視界が開けることと本に囲まれることという理由の差を残す。誘導的な質問でAIが決めた性格へ誘導しない。

**受入条件：** 共通用途と異なる理由が同時に保存・表示される。

#### SELF-003 条件を限った訂正

**位置付け：既存要件／重要度：必須／工程：G1/G2／元参照：R自己§2／A24–25**

「この日は急いでいただけ」の適用をその体験へ限定する。過去の記憶と今の好みを両立させ、有効な本人訂正をAIが黙って解除しない。

**受入条件：** 現在の訂正で過去の体験文が消えず、再推論後も訂正範囲が守られる。

#### SELF-004 週・月・年の統計

**位置付け：既存要件／重要度：必須／工程：G2／元参照：R自己§3**

移動、訪問、新しい場所・地域、時間、用途・理由・変化を集計し、記録率や不明分を示す。位置記録がない日を活動ゼロとみなさない。

**受入条件：** 異なる記録量の週を比較する際に欠測が見え、移動距離の不明を0にしない。

#### SELF-005 診断機能の内容

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：R自己§4の具体化**

パーソナリティ診断を削除せず「街との付き合い方：状況別の行動プロファイル」として実装する。固定型や臨床診断ではなく、どの状況で何を優先しやすいかという検証可能な仮説を示す。

**受入条件：** 各記述に対象状況、根拠、反例、更新日、未確認点が付き、データ不足では保留される。

#### SELF-006 申告・選択・制約・結果

**位置付け：今回の追加・変更提案／重要度：必須／工程：G1/G2／元参照：W10–12／今回ユーザー指示**

本人の申告、実際に提示した選択肢、その時点の実行可能性、選択、訪問後の目的適合を別に保存する。行かなかっただけの場所を嫌いと学習しない。

**受入条件：** 提示されなかった候補・休業候補・通学上必須の訪問を自由な好みと混同しない。

#### SELF-007 小標本での選好モデル

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：W10–12**

状況との交互作用を含む少数の解釈可能な属性を用い、正則化した二者選択モデル等で選びやすさを更新する。LLMは抽出・説明・質問に使い、根拠なしに重みや確信度を作らせない。

**受入条件：** 入力とモデル版を固定すると順位を再現でき、データ不足時は強い性格結論を返さない。

#### SELF-008 一つだけ聞く能動的質問

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：R自己§2の拡張／W11**

候補の順位や解釈を分ける有用な質問を1つ選ぶ。情報利得だけでなく回答負担と機微性を考慮し、回答しない選択も尊重する。初期はルール選択、後に事後分布に基づく選択へ接続できる契約とする。

**受入条件：** 答えても候補が変わらない質問を優先せず、同じ根拠の質問を反復しない。

#### SELF-009 反例と説明の比較

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：今回提案**

「静かだから選んだ」「近いから選んだ」「時間がなかった」等の競合仮説を本人が選び直せる。反例を隠さず、訂正前後で同じ候補集合に対する順位・理由の差を示す。

**受入条件：** 文章だけでなく次の選択が変化し、訪問の事実と本人が確認済みの用途は勝手に変更されない。

#### SELF-010 予測の検証

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2/G5／元参照：W10–12**

振り返りの納得感だけで正しさを判定せず、その後の別場面の選択・目的への適合で仮説を点検する。2体験という既存条件は仮説生成の下限であり統計的な検証完了ではない。

**受入条件：** 学習に使った体験と評価体験を区別し、根拠数と評価対象数を別に表示できる。

#### SELF-011 望む自分と観測された自分

**位置付け：今回の追加・変更提案／重要度：必須／工程：G2／元参照：今回提案**

よく行く場所に閉じ込めず、「今日は新しい体験をしたい」等の現在の希望を優先する。習慣的行動と本人が望む探索を別に保持する。

**受入条件：** 頻回訪問に反する希望を明示すると条件を守った新規候補が出る。

#### SELF-012 日記

**位置付け：既存要件／重要度：望ましい／工程：G2／元参照：R自己§5**

日記として体験を残し、AIの下書きは本人が承認・編集する。出来事、本人の表現、AIの補足を区別し、共有を自動化しない。

**受入条件：** AIが書いた架空の体験が承認なしに日記の事実へ混ざらない。

#### SELF-013 発見を戻す

**位置付け：既存要件／重要度：必須／工程：G2/G3／元参照：R自己§6**

本人が確認した用途は建物に、現在の希望・条件は推薦に、許可した内容は比較へ反映する。仮説の成立と訪問の成立を分離する。

**受入条件：** 診断の訂正だけで訪問数は変わらず、用途訂正は正しい建物に反映される。

#### SELF-014 非医療・非センシティブ推定

**位置付け：今回の追加・変更提案／重要度：必須／工程：G1／元参照：大会規則／今回ユーザー意向**

地域や移動から疾患、宗教、政治、性的指向等の個人属性を推定しない。性格型・人口内パーセンタイル・医学的改善を検証なしに主張せず、友人の相性をデーティング用途へ転用しない。

**受入条件：** 機微な場所の訪問でセンシティブ診断が生成されず、共有プロファイルが本人承認に限定される。


### EXT 要件

#### EXT-001 ストアの入口

**位置付け：既存要件／重要度：必須／工程：G4／元参照：Rアプリ§1**

困りごとや名称でプラグインを検索し、作者、機能、版、対応環境、データ、権限を読んでアプリ内から導入する。一般利用者にCLI・GitHub・手作業配置を要求しない。

**受入条件：** 通常利用者がストア→詳細→権限→導入→機能利用までアプリ内で完了できる。

#### EXT-002 導入の状態

**位置付け：既存要件／重要度：必須／工程：G4／元参照：Rアプリ§1・4**

進行、成功、失敗、開く場所を示し、導入済み一覧から設定、無効化、削除、更新、検証済み旧版への復帰を行う。失敗した更新で動く旧版を壊さない。

**受入条件：** 通信切断や検証失敗で既存版が保持され、追加権限は改めて確認される。

#### EXT-003 3種類すべての実演

**位置付け：既存要件／重要度：必須／工程：G4/G5／元参照：Rアプリ§2・5**

防災、バイク、聖地巡礼の3種を準備し、インストールから利用までそれぞれ実演・検証する。どれか一つだけを動かして3種完成とは扱わない。

**受入条件：** 3種すべてに入力・権限・導入版・実行出力・失敗状態の記録がある。

#### EXT-004 防災プラグイン

**位置付け：既存要件／重要度：必須／工程：G4／元参照：Rアプリ§2**

浸水想定、取得できる時点の浸水・地域情報、避難先と経路を出典・時刻付きで表示する。想定と実況、通行確認と未確認を区別し、安全保証や災害中の運用認証を主張しない。

**受入条件：** 未取得を浸水なしと表示せず、経路が安全未確認なら通常の到達計算と区別する。

#### EXT-005 バイクプラグイン

**位置付け：既存要件／重要度：必須／工程：G4／元参照：Rアプリ§2**

対象車種・排気量区分・時間帯の根拠付き制限を確認して走行可否と経路を表示する。自動車経路の色替えだけにしない。未確認区間を走行可としない。

**受入条件：** 対象クラスの禁止道路と時間制限を除外でき、データ不足は確認不能として返る。

#### EXT-006 聖地巡礼プラグイン

**位置付け：既存要件／重要度：必須／工程：G4／元参照：Rアプリ§2**

作品・場所の関連と出典、巡回案を扱う。施設への立入り、撮影、掲載素材の権利を確認し、ファン推測と公式関連情報を区別する。

**受入条件：** 関連場所の根拠へ到達でき、作品画像を権利未確認のまま配布しない。

#### EXT-007 GitHub開発導線

**位置付け：既存要件／重要度：必須／工程：G4／元参照：Rアプリ§3**

開発者向け入口として公開可能なGitHubガイド、Codex用手順、テンプレート、入出力契約、権限、例、テスト、エラー、更新・修復・版管理を提供する。

**受入条件：** 作者以外の人がガイドだけで新しい機能を作成・検証・インストールできる。

#### EXT-008 本当の新規コード拡張

**位置付け：既存設計案を継承／重要度：必須／工程：G4／元参照：S実装§10／A34–35**

設定型と新しいコード型を両方扱う。固定3プラグインのON/OFFだけにせず、初期語彙にない計算・表示・情報源を追加できる。最初の生成例として寄り道5分以内の休憩場所計算を保持する。

**受入条件：** 定義されていなかった計算が生成コードとして実行され、追加前にはできなかった出力を返す。

#### EXT-009 生成から導入までの証跡

**位置付け：今回の追加・変更提案／重要度：必須／工程：G4／元参照：S実装§10–11の強化**

要求、Codexによる変更、固定された独立テスト、成果物ハッシュ、プレビュー、承認、導入、実行、復帰を一本で追えるようにする。開発ツールとしての利用と製品拡張としての利用を別々に説明する。

**受入条件：** 生成した版・テストした版・導入した版のハッシュが一致する。

#### EXT-010 編集範囲とテストの独立

**位置付け：既存設計案を継承／重要度：必須／工程：G0/G4／元参照：S実装§10・12／A36・45–46**

Codexに変更可能なファイルと合成入力を渡し、本体、私有履歴、秘密、独立テストの期待値を変更範囲へ入れない。テスト変更で失敗を成功にしない。

**受入条件：** 検証後改変・期待値書換え・権限追加が検出され、有効化できない。

#### EXT-011 能力単位の権限

**位置付け：既存設計案を継承／重要度：必須／工程：G0/G4／元参照：Sデータ§7／A37–38**

端末側コードは宣言した共通操作とデータ項目だけ使う。通信は許可先・パス・メソッド・リダイレクト・量を検査する仲介に限る。DB資格情報、session cookie、親DOM、任意ファイルへのアクセスを渡さない。

**受入条件：** 未許可の個人データ・外部送信・ローカルネットワーク・親DOMへのアクセスが拒否される。

#### EXT-012 端末実行と隔離

**位置付け：既存設計案を継承／重要度：必須／工程：G0/G4／元参照：S実装§10.2／Sデータ§7**

コードと専用画面は端末側の制限実行環境と隔離表示に分ける。Dockerを必須にしない。Workerやiframeを置いただけで通信・無限ループ・メモリ制限が完了したと見なさない。

**受入条件：** 停止、出力上限、通信禁止、親表示の無応答回避をSimulator環境で検証する。

#### EXT-013 外部接続の現実性

**位置付け：既存設計案を継承／重要度：必須／工程：G0/G4／元参照：S実装§10.2**

端末から取得可能な公開情報は端末の許可済み仲介で取得する。CORS未対応や運営秘密キーが必要な接続は事前定義した運営APIで仲介する。任意の新規サーバーコードの実行は従来どおり初期対象外とする。

**受入条件：** CORSやキー未設定を動作済みとして隠さず、生成コードに秘密が含まれない。

#### EXT-014 表示拡張と入力

**位置付け：既存設計案を継承／重要度：必須／工程：G4／元参照：Sデータ§7**

GeoJSON、カード、評価、独自表示データ、許可された入力を追加可能とする。任意HTMLを本体へ挿入せず、Schema、サイズ、地域範囲、送信元・nonceを検証する。

**受入条件：** 無効な座標・巨大出力・偽メッセージ・スクリプト注入を拒否する。

#### EXT-015 共有・複製・復帰

**位置付け：既存設計案を継承／重要度：必須／工程：G4／元参照：S実装§10・13／A39–41**

機能コード・条件と私有データを分離して共有・forkする。独立して許可取得したコード複製と、元情報への利用権は別物とする。元情報を取消したら私有入力を再利用しない。

**受入条件：** コードforkは保持できても元作者の取消済み位置・理由へアクセスできない。

#### EXT-016 5形式の情報取込み

**位置付け：既存設計案を継承／重要度：必須／工程：G4／元参照：S実装§12／A42**

API、CSV、GeoJSON、HTML、PDFの各入力に変換器と検証例を持たせる。原資料の箇所、座標系、単位、観測・公開・取得・期限の意味を保持する。

## 8. 主要シナリオと画面間の接続

### SC01：履歴なしで、最初の建物を育てる

ホームまたは地図 → 場所を選ぶ → 「ここで本を読んだ」等の一言 → 本人申告の体験を保存 → 任意の一問 → 明示的に3Dへ → 用途に対応した建物を表示 → 自分を知るに同じ原文と用途が現れる。

位置権限なし・GPS履歴なし・友人なしでも通す。過去体験を話すことと現在訪問したことを混同しない。最初の変化まで60秒以内を初回ユーザーテストの仮目標にするが、達成済みの数値としない。

### SC02：普段の帰り道からクエストへ

有効な定期情報と最終目的地 → 「今日は30分だけ寄りたい」 → 追加運賃と寄り道移動＋滞在を満たす候補 → 地図上で通常案内 → 訪問確認 → 次回の建物成長と振り返り。

20分等の時間や0円はAPIで確認できた場合だけ実額として示す。条件が合わなければ不足条件を出す。実演のための入力が合成ならそう表示する。

### SC03：仮説を訂正して、その後を変える

自分を知る → 条件付きプロファイル → 根拠を開く → 「静かな場所を選んだのではなく、この日は時間がなかった」 → 当該体験の仮説を訂正 → 同じ候補集合で再推薦 → 順位と理由が変わる → 再読込みしても訂正が残る。

体験の事実や確定用途は、別途訂正しない限り変えない。これは本人が直せることと、直した内容が実処理へ届くことを示す中心的な実演とする。

### SC04：同じ場所の違いと、違う場所の共通点

みんなで育てる → 目的または場所で検索 → 同じカフェの勉強と会話を比較 → 相手の理由を表示 → 川辺と本屋の共通用途を比較 → 合う/違うを訂正 → 友人レンズまたは移し替えへ。

同じ駅の別ランチ、同じ公園の休憩、見慣れた建物の新用途も独立した受入例として通す。別都市の対応はカードまたは明確に異なる記号で示し、移動経路線を描かない。

### SC05：別の街で、あの体験を試す

共有された元体験 → 体験レシピを確認 → 行き先都市と自分の時間・交通条件 → UAS/カテゴリ/公開情報から候補取得 → 経路・条件検証 → 忠実案/自分向け案 → 変更明細 → 案内 → 自分の感想を保存。

推奨地域は名古屋と東京。比較対象の実施設・道路・メッシュを実装前に確認し、架空の店を実在の候補にしない。横浜・箱根で試す場合、未確認のUASを使わないこと以外は同じ機能を使う。

### SC06：共同のお出かけ

二人の許可された希望 → 本屋に寄りたい人と水辺に寄りたい人 → 各人の必須条件と時間 → コース案 → 誰の希望がどこで満たされるか → 各人の確認 → 明示的な送信。

一人の希望を平均点のために消さない。実現できない場合は変更候補を選んでもらう。共同行動の成立を、性格の相性診断と混同しない。

### SC07：3種のストア導入

アプリを育てる → 防災を検索 → 出典・データ・権限を確認 → 導入 → 対象地域の想定/時点情報と経路を開く。同じ入口からバイク、聖地巡礼もそれぞれ導入→利用→無効化→再有効化を確認する。

3種はテーマ名だけ違う固定地図ではなく、必要データ・制約・表示の異なる機能である。通常利用者はGitHubへ行かなくてよい。

### SC08：Codexで新しい機能を作る

開発者がGitHubのガイド → 「この散歩から寄り道5分以内の休憩候補と追加時間を出す」 → 新規コード生成 → 独立した境界値・到達不能・根拠欠落テスト → プレビュー → 検証ハッシュと一致した版を登録 → ストア導入 → 自分の地図で実行。

旧例の仕様を保持する場合、経路上の接続点候補から休憩地点への往復を追加歩行時間とする。全地点について大域的な最短寄り道を保証するものではない。休憩の滞在時間は別に合算する。

### SC09：情報源が壊れたとき

平常の地域情報取得 → CSVの座標列名称が変わる → 解析失敗 → 元データ・旧変換器・契約をCodexへ → 変換器だけ修復 → 元のテストで確認 → 承認 → 通常更新復帰。

次に単位の意味を変えた入力を与え、修復したふりをせず保留する。ネットワーク障害で毎回コードを書き直さない。期待値を修復エージェントに変えさせない。

### SC10：共有取消・削除・途中失敗

相手が用途だけ共有 → 生成中に取消 → 旧結果の公開を拒否 → 開いている比較・会話・保存候補から私有引用が失効 → 受信者自身の新しい体験は保持。

別途、AI失敗後の原文再利用、写真取消、ストア失敗時の旧版維持、SSE切断、並行訂正、位置不明区間、API未設定も確認する。オフライン端末・スクリーンショット等を遠隔で消せるとは説明しない。

### SC11：同じ建物の異なる階

同じ2D位置の地下と上層の体験 → 階の根拠と不明を表示 → 用途を分ける → 入口・上下接続を確認 → 自分/友人レンズで違いを比較。

確かな階データがなければ階番号を推測で確定せず、本人の申告と不明を保持する。3Dの見た目だけで上下の移動可能性を保証しない。

### 8.1 引継ぎ対象の契約

| 移動 | 引き継ぐもの | 引き継がないもの |
|---|---|---|
| 地図→自己 | 対象体験・場所・期間・本人の原文と版 | 相手レンズの私有データを本人の経験にしない |
| 自己→地図 | 確認した用途/理由、訂正、希望、元カメラ | 未確認仮説による訪問数の変更 |
| 比較→移し替え | 元体験版、用途/理由/順序、許可範囲 | 共有されていない原文、精密履歴 |
| 移し替え→案内 | 選んだ候補版、条件、検証済み経路 | 未選択候補による既存案内の自動上書き |
| ストア→地図 | 導入版、権限、入力対象、結果の出典 | 作者の秘密、作者自身の非公開履歴 |
| 体験→返信 | 本人が選んだ結果と共有範囲 | 自動的な全行程・現在位置公開 |

### 9.1 全体工程

| G0 成立性と環境 | 大会の既存資産確認、API認証/券種、建物置換、UAS実収録/権利、端末コード隔離、Simulator | それぞれの小さな実試験で外部条件と技術上の入口が確認される | 素材の出典整理、3プラグインの情報源調査、基本契約 |

G4の実装をG3が終わってから始めるという意味ではない。**G0でランタイムを検証し、G1から契約に沿って並行開発し、G4で全体へ統合する。** 交通も同様にG0から実接続を調べる。

4人チームの場合の推奨分担は、地図・操作、共通データ・自己理解、比較・移し替え・交通、プラグイン・Codex・情報源。人数は未確認であり、4人が確保済みとはしない。2人の場合は同じ仕事を2系統に束ねるが、工数が半分になるとは考えない。

### 9.2 大会までと当日の区別

公式ルールは2026年9月15日9:00〜21:00の公式開発期間に実質的に開発することと、重要な既存資産の書面開示を求める[W01]。この時間全てがコーディングに使えるとは限らず、第1段階の提出締切・ピッチ時間は別に確認する。

事前は設計、契約調査、環境、入力候補、利用権、既存資産の開示内容を整理する。事前PoCや試作コードを本番へどこまで持ち込めるかは主催者の明示条件を確認し、許可されていない再利用を前提に工程を短縮しない。

当日は最初の作業時間帯でG1と各トラックの最小接続を合わせ、途中で一度「記録→意味→地図」の通し動作を合流させる。その後もトラック単体完成を待たず、同じデータ契約へ小刻みに統合する。最後の枠はピッチ作成だけでなく全体受入と負例の修正に確保する。

G0の検証が失敗した場合は、条件を満たす実装方式・プロバイダーを比較して切り替える。機能を消したり、実APIを保存済み表示で偽装したりして工程を完了にしない。未確保の外部条件を残したまま、全量が当日完成すると約束しない。

## 10. 審査に対する見せ方

### 10.1 審査基準との対応

公式の第1段階はCodex活用、実世界へのインパクト、再利用・展開、デモ/ピッチ、参加者投票の考慮が各20%。最終段階は投票以外の4軸が各25%。同点時はCodex活用、次いで実世界へのインパクトで判断される[W01]。

| 軸 | 見せる証拠 | 避ける説明 |
|---|---|---|
| Codex活用 | 新規機能の要求→差分→独立テスト→実行、壊れた情報源の修復、当日の開発履歴 | 「何万行書かせた」「ほぼAIで作った」だけ |
| 実世界へのインパクト | 時間・追加費用・理由に合う具体的寄り道、他者の使い方の発見、訂正の反映 | 根拠のない社会課題の巨大化、災害時安全の断定 |
| 再利用・展開 | 共通の体験レシピ、地域manifest、3種の拡張、第三者が作れるガイドとテスト | GitHubリンクがあるだけで再現できるとする |
| デモ/ピッチ | 一言で街が変わる、訂正で候補が変わる、別都市へ意味が残る | 全画面を順にクリックして終わる |
| 参加者への伝わりやすさ | 自分の「ここをこう使う」に置き換えられる短い体験 | 研究名と安全機構の説明から始める |

### 10.2 短い主実演と完全実演

発表時間が未確定なので、以下は**3分版の仮構成**。公式の時間制限ではない。全機能の完成・実演要件を3分に押し込めて緩める趣旨ではなく、詳細デモ・操作可能状態・検証記録も用意する。

| 目安 | 主実演 | 見せる変化 |
|---|---|---|
| 0:00–0:20 | 「同じカフェでも、私には作業場、友人には話す場所」 | 場所のカテゴリでは表せない違い |
| 0:20–0:45 | 一言記録→3Dで象徴建物へ | 自分の経験が街の形になる |
| 0:45–1:15 | 「静かだからではなく時間がなかった」と訂正 | 同じ候補の順位が変わり、理解を直せる |
| 1:15–1:55 | 友人の体験レシピを別都市へ | UASによる地域候補と、役割/順序/条件が残る |
| 1:55–2:25 | Codexが作った新しい計算の差分・テスト・導入・実行 | 既存3種の切替だけではない拡張性 |
| 2:25–2:45 | 実際の感想を戻す | 地図・自己理解・次の行き先が一つにつながる |
| 2:45–3:00 | 第三者再現と3種の導入済み機能を示して締める | 展開可能性と完成範囲 |

3種すべての「インストール→利用」は詳細実演でそれぞれ通し、単に導入済みアイコンを映したことを受入合格にしない。新規コードの生成が発表尺を超える場合、会場内で実行して得たログ・成果物とその場の実行を区別して示す。生成動画をライブ生成と称さない。

ピッチの締め：

> 私たちが育てるのは、訪問数ではありません。なぜその場所を選び、そこで何を得たかという理解です。その理解が自分の街を変え、他人の体験を使えるようにし、知らない街へ持ち運べます。そして必要な機能そのものもCodexで育てられます。

### 10.3 追加の検証計画

大会前後に行う小規模な試用は、例えば8〜12人・各4〜6場面から始める。人数は研究上十分とする基準ではなく、募集可能性を確認するための計画仮定である。短期の試用で人格診断の妥当性や長期継続率を証明しない。

評価は、初回完了、質問負担、目的適合、移し替えの忠実さと受け手適合、未使用場面の予測、訂正の維持、制約違反、プラグイン第三者再現を分ける。順序効果を抑えるため方法の提示順を入れ替え、どの方式か伏せられる評価は伏せる。人数・場面数・除外理由・失敗も報告する。同じ参加者の多数の選択を独立した多数人の証拠と扱わない。

OpenUASの追加効果が確認できなければ「研究資産だから優れる」と売り出さない。機能を消すのでなく、どの条件で役立ち、どこで根拠が足りないかを可視化し、取得方法を改良する。

## 12. Stage2へ渡す技術制約と設計上の仮定

### 12.1 決定していることと決めること

確定側は、4タブと導線、Mapboxベース、PLATEAU全面導入をしないこと、Node.js/Bun、Mac直接のPostgreSQL＋PostGIS、Supabase不採用、Docker非必須、端末側プラグイン、通常利用者のストア導入、開発者のGitHub導線、今回のMac仮想端末通しデモという既存方針。

Stage2で決めるのは、現行Viteをどう移行/利用するか、最終UIフレームワーク、DB投影と索引、ジョブ実装、描画の方式、交通事業者のAPI、場所データの保存条件、QuickJS等の隔離方式、具体的なモデルと推定法、認証導入時の接続先、テストの実装である。既存案のNext.jsを合意済みとして固定せず、変更時には価値・工数・互換性を説明する。

共通境界は、記録取込み、本人の説明、根拠と訂正、権限付き比較、体験レシピ、候補取得、経路と条件検証、診断、地図表現、機能の版/実行、外部情報、検証証跡。LLMに委ねる処理と確定的に検証する処理を分ける。特定のフレームワークのデータ形に全ドメインを従属させない。

### 12.2 値と状態の原則

時刻はUTC保存・Asia/Tokyo表示、WGS84のGeoJSONは経度/緯度の順、距離m、時間差s。不明はnullとする。施設ID、建物ID、階ID、体験ID、訪問IDを区別する。同じ店名だけで施設を統合しない。

原記録、確定した状態、解釈、計算結果は別に持つ。生成物には元の入力・データ版・共有版・モデル/プロンプト/契約版・成果物ハッシュを残す。公開直前に版が変わった場合の扱いまで設計する。全体のデータ形式を汎用JSONへ押し込んでSchema検証を省略しない。

| 2D「地図を見る」 | 地名・道路・施設・現在地・軌跡・保存場所・経路を俯瞰する。移動・拡大縮小・場所選択ができ、成長や用途は色・輪郭・アイコンで示す |
| 3D「地図の世界に入る」 | 現在地の人形を中心に、訪問による建物の立ち上がりと成長を見る。追従・回転・拡大縮小ができ、いつでも2Dへ戻れる |

3Dは専用の操作で開き、場所のタップでは自動で切り替えない。切替時は建物・人物・操作・追従方法を合わせて変え、現在地との関係を保つ。2Dへ戻ると元の表示範囲を復元する。動きを減らす端末設定では大きなカメラ移動や変身演出を省く。

### 今いる場所を記録し、不明な区間を補う

日常の記録は「地図を育てる」で行う。自分レンズに「今ここにいる」などの入口を置き、現在地や選んだ建物・施設と時刻を確認して、滞在・訪問を記録できるようにする。自動取得した訪問候補も、その場で確認・訂正できる。

地図と時系列に、欠損区間と、位置や訪問先が曖昧な区間を示す。タップして候補選択・場所検索・地図上の指定で補える。「この時間はこの店にいた」「この駅から電車で移動した」といった短い入力からも補完案を作れる。

場所・おおよその時間・移動手段を分かる範囲で入力する。正確な経路や時刻は必須にせず、不明・後回しも選べる。既存記録を下書きにして訂正できるようにする。

### 記録のついでにAIが話を聞く

記録や補完のついでに、AIが「ここでは何をしていた？」「どうだった？」と1問ずつ尋ねる。用途・理由・感想を整理し、本人が確認・訂正する。回答は任意で、会話なしでも場所を記録できる。

本人が伝えた内容とAIの補完案、測位による記録を区別する。AIが作った場所・時間・移動の補完案は、本人が確認してから記録に反映する。端点だけから正確な移動経路を作らず、概略の申告は概略のまま保持する。

記録・補完・訂正は同じ体験に結び付け、訪問を重複登録しない。確認された訪問は建物の成長へ、用途は外観へ反映し、「自分を知る」の振り返りにも引き継ぐ。保存失敗時は入力を保持して再試行できるようにする。

## 2. 訪問と用途で建物が育つ（必須）

### 訪問すると立ち上がる

訪問した建物が3Dで立ち上がり、その状態が蓄積される。2D中の訪問も保存し、3Dへ切り替えた際に反映する。

訪問済みと背景の未訪問建物を見分けられるようにする。通過は軌跡・解放範囲で表し、閲覧、経路検索、AIの推薦、他者の共有だけでは訪問済みにしない。

### 用途によって姿が変わる

自分レンズの3Dでは、本人が用途を登録・確認した建物を、その意味を象徴するランドマークへ置き換える。

| 用途 | 造形の参考案 |
|---|---|
| 勉強する場所 | 大きな本をかたどった建物 |
| 友人と話す場所 | 吹き出しが集まった建物 |
| 一人で休む場所 | 木陰や小さな庭 |

施設の業種ではなく、本人にとっての用途を反映する。複数用途を扱い、表示しきれない用途も確認できる。用途の追加・変更・削除は外観へ反映する。用途未登録なら通常の建物を表示し、訪問済みであれば立ち上がった状態を保つ。

レンズ表現を外すと、地図データに基づく元の建物形状を確認できる。置換後も位置・道路・施設名・案内に必要な入口との対応を保ち、現地の外観とは区別する。他人レンズでは、共有された用途に応じて同じ場所が別の姿になる。

### 通うほど造形・装飾が育つ

訪問を重ねると、用途のモチーフを保ちながら造形・色・縁取り・輝き・装飾が段階的に変わる。本が増える、庭が豊かになるなどの表現を検討する。2Dはマーカー、3Dはランドマークやアイコン・装飾で同じ成長段階を示す。

![訪問に応じて育つ用途マーカーの参考](references/visit-growth-marker-reference.png)

ユーザー提供画像の5段階を試作の参考とする。段階数・配色・名称・訪問回数は未確定。「お気に入り」「特別な場所」は訪問回数だけで決めず、本人の意味付けと区別する。画像のアプリ素材への採用は別途決める。

用途と成長段階は両方読み取れる表現にする。色だけに依存せず、用途名やアイコンでも意味を確認でき、選択中・AIのおすすめ・訪問済みの表示と混同しない。装飾が育っても道路や案内を隠さない。

### 成長の記録

訪問・用途・建物や施設・所有者・根拠を結び付け、成長段階を保存する。同一訪問の位置更新や再読込を重複加算しない。用途の変更や削除でも訪問の蓄積を保ち、再起動後に復元する。AIの推定用途は本人の確認済み用途と区別する。

## 3. 行き先の提案

### 自動クエスト

自分レンズでは、AIに質問しなくても「ここに行ってみない？」と提案する。現在地・表示地域・好み・訪問記録・定期区間・友人の共有情報を使う。友人や履歴がない場合も、利用可能な地域情報から提案する。

| きっかけ | 例 |
|---|---|
| 友人の訪問 | 「フレンドの○○さんも行っていたよ」 |
| 自分の好み | 「近くでもう一つ、一人で休める場所を探してみない？」 |
| 寄り道 | 「定期区間内で、帰りに30分寄ってみない？」 |
| 地図の成長 | 「まだ訪問記録のない建物を訪れてみない？」 |

アプリ内のカードなどに、行き先・理由・達成条件・所要時間・距離・分かる場合は追加運賃を表示する。「行ってみる」から詳細と案内へ進み、同じ提案についてAIへ相談できる。「あとで見る」「今回は見送る」と自動提案オフも用意し、案内を遮ったり見送り直後に再表示したりしない。

友人の訪問を理由にする場合は、閲覧可能な訪問記録や投稿を根拠として示す。場所の保存を訪問に、過去の訪問を現在地に読み替えない。共有取消後は提案と理由から対象情報を外す。

実際の訪問で達成し、建物の成長と写真・感想・用途の記録へつなぐ。提案の閲覧・受諾・経路検索だけでは達成にしない。提案先・理由・参照元・達成条件と、あとで見る／見送り／進行中／達成の状態を保存する。

### 定期区間内の寄り道（特色）

「帰りに30分」「追加運賃なし」などを指定し、定期区間の駅・停留所から寄れる、まだ訪問記録のない場所をAIが提案する。徒歩区間と最終目的地までを含むコース、追加時間・運賃・理由を示す。区間外を許容するときも費用を明示し、候補がなければ条件変更へ戻る。

AIのおすすめ、クエスト、寄り道、友人との共同コースは、次の案内機能へ接続する。

## 4. 経路案内・乗換案内（必須）

両レンズで利用でき、AIとの会話なしでも目的地を指定して使える。

| 機能 | 必要な操作・情報 |
|---|---|
| 目的地の指定 | 場所名・住所・駅名の検索、地図や建物の「ここへ行く」、保存場所から開く。出発地は現在地を初期値とし、手入力で変更できる |
| 徒歩案内 | 経路・距離・所要時間・目的地・主な曲がり角を表示。開始後は現在地・次の方向・残りの距離と時間を示す。終了と経路を外れた際の再検索ができる |
| 乗換案内 | 出発日時・到着希望日時を指定。鉄道・バスと徒歩を含む候補の出発／到着時刻・所要時間・乗換回数・運賃を比較する |
| 乗換の詳細 | 路線・行先・乗降駅や停留所・乗換順序・各区間の時刻を示す |

時刻・運賃・運行情報は交通データに基づき、取得できない項目は不明とする。AIで補完せず、時刻表の予定とリアルタイム情報を区別する。

### 定期券を考慮する（必須）

定期券の区間・交通事業者・経由路線・有効期間を登録・編集・削除できる。検索時に利用の有無を選び、指定日時に有効な定期券で追加運賃を計算する。

候補ごとに通常運賃・追加運賃・所要時間・乗換回数を示し、速さを優先する経路と追加運賃を抑える経路を比較する。適用区間と追加費用の発生区間を分け、期間外は適用しない理由を示す。適用可否や金額が不明な場合は、追加運賃なしと表示しない。

定期券は本人の移動条件として保存し、他人レンズでも本人のものを使う。

## 5. 写真と場所への意見

### 写真を撮って投稿する

写真を撮影し、投稿先の場所・本文・公開範囲を確認して投稿する。写真を場所と本人の体験に結び付け、地図から確認できるようにする。撮影場所を取得できなければ手動で選べる。撮影取消時は投稿しない。

### 建物詳細（望ましい機能）

両レンズで建物をタッチすると、他の人にとってどんな場所かを用途・体験・写真・意見から知り、自分の意見も投稿できる。

投稿者・時点・対象を示し、異なる意見を残す。AIの要約から元の投稿を確認でき、「みんな」は閲覧可能な投稿の範囲を指す。意見がなければ最初の投稿へ案内する。建物全体と個別施設を投稿先として選び分ける方法は検討する。

## 6. 保存・失敗時・タブ間の接続

移動・訪問・写真・場所との関連・公開範囲を保存する。タブ、レンズ、表示を切り替えても、選択中の場所・地図範囲・経路・案内状態・記録を保つ。レンズ変更だけで案内中の経路を置き換えない。

検索・推薦の処理中、候補なし、地域や交通手段の未対応、通信失敗を区別する。失敗時も地図と既存記録を表示し、条件や編集中の写真・本文を保って再試行できる。位置情報を失ったら更新停止を示し、手動で出発地や場所を選べるようにする。

「みんなで育てる」から友人の共有視点・共同コースを受け取り、「自分を知る」へ振り返る日付・場所・記録を渡す。

## 7. 受入条件

| 確認する体験 | 完了の判断 |
|---|---|
| レンズと表示 | 自分・他人・ペルソナを識別でき、2D・3Dと独立して切り替えられる |
| その場の記録と補完 | 地図から現在・直前の滞在を記録し、欠損・曖昧な区間を候補選択や短い入力で補える。不明を残せ、AIへの回答なしでも保存できる |
| 補完の根拠 | 測位・本人の申告・AIの案を区別し、確認後に重複なく反映する。概略の経路や時刻を実測として扱わない |
| 建物の成長 | 初訪問で立ち上がり、用途で姿が変わり、再訪で育つ。元の形状も確認でき、重複計上・用途変更・再起動で記録が崩れない |
| クエスト | 質問なしで提案され、理由と条件を確認し、案内・保留・見送り・オフを選べる。実訪問で達成し、共有取消を反映する |
| 経路と乗換 | AIを経由せず検索・比較・案内開始／終了ができ、時刻・運賃の不明と取得失敗を識別できる |
| 定期券と寄り道 | 定期券を管理し、期限と区間に応じた費用を比較できる。徒歩・最終目的地を含めて寄り道条件を評価する |
| 写真・意見 | 写真を場所・公開範囲付きで投稿し、失敗時に再試行できる。建物詳細を採用する場合は両レンズから意見を読み書きできる |
| 状態の保持 | タブ・レンズ切替後も案内と記録を保持し、他者の情報を本人の訪問として扱わない |

## 現在地の表示

2Dと3Dでは、それぞれの表示目的に合う現在地表現を使用する。

| モード | 現在地の表現 |
|---|---|
| 地図を見る | 地図で一般的な現在地パック。位置、向き、測位精度を地図の読みやすさを損なわずに示す |
| 地図の世界に入る | 頭、胴体、手足が判別できる簡素な人形。現在地と進行方向を示し、街の表示を隠さない大きさにする |

3Dの人形は、次の条件を満たす。

- 特定の年齢、性別、人物像を強く想起させない中立的な外観とする。
- 初期版では着せ替え、容姿の編集、複数キャラクターの選択を設けない。
- 有効な方角を取得できる場合は、その方角へ向ける。
- 方角を取得できない場合は、直前の有効な移動方向を維持し、根拠のない向きへ回転させない。
- 有効な移動を検出した場合だけ歩行モーションを再生する。測位の揺れだけで歩行させない。
- 停止中、記録中、測位精度が低い状態を、人形または足元の表示で区別できるようにする。
- カメラを回転しても現在地と進行方向を読み取れるようにする。

人物の周囲から街が育つ表現を製品固有の体験とし、人形は簡素にする。造形は次の画像を基準とする。

![3D簡易人形の造形参考](references/simple-walker-reference.png)

大きな多面体の頭、細い胴体、関節の分かる簡略化された手足、まとまりのある手先と足先で構成する。顔、髪、服、指、肌の質感などは作らず、全身を一つの無地の素材で表示する。小さく表示しても人と進行方向が分かり、地図や建物より目立たない造形にする。特定作品の形状や意匠はそのまま複製しない。

人形には簡素な骨格を入れ、左右の足の接地、足上げ、大きめの腕振り、重心の上下動が一続きに見える短く軽快な歩行サイクルを持たせる。移動速度に合わせて再生速度を調整し、停止時は歩行途中で固めず自然な立ち姿へ戻す。造形は簡素にするが、滑って移動しているように見えない歩行品質は確保する。

初期試作では、George Blackwellの「Super Basic Human Model w/ Animations」を使用する。配布元は `https://georgeblackwell.itch.io/basic-human-mesh`、ライセンスはCC BY 4.0であり、作者名と配布元をアプリまたは同梱資料に表示する。これはMapbox上で大きさ、視認性、歩行品質を確認するための仮採用であり、最終版の造形確定とは区別する。

## モードの切替

- 2Dから3Dへの切替は、地図上の通常操作と区別できる明示的な操作にする。
- 切替時には、現在見ている場所または現在地との関係を失わないようにカメラを移動する。
- カメラ移動だけでなく、3D用の建物、人物、操作UI、追従方法を同時に切り替える。
- 3Dから2Dへ戻った場合は、3Dへ入る前に見ていた範囲へ戻ることを基本とする。
- 動きを減らす端末設定が有効な場合は、大きなカメラアニメーションを省略する。

切替操作の最終的な表示名は未決とする。「地図の世界に入る」「3Dで歩く」「街の成長を見る」を、記録開始との関係を決めた後に比較する。

## 地図の技術基盤

Mapboxを採用する場合は、Mapbox Standardを通常の地理情報の基盤とし、標準の3D建物をそのまま成長表現として使わない。

PLATEAUはLOD2の素の表示とアニメ調表示を試作比較した結果、求める見た目とのずれと読み込み負荷が大きいため採用しない。通常の地理情報はMapbox Standardを使い、不足するランドマークだけを根拠と利用条件を確認した外部モデルで補う。

- 2Dでは、地名、道路、施設を確認できる淡い背景地図を表示する。
- 3Dでは、独自に管理する探索状態と建物データを使って、育った範囲を表示する。
- 軌跡、解放範囲、場所、記憶、AI提案経路は独自レイヤーとして重ねる。
- 記憶、AI提案、気になる場所は、対象建物を選択したうえで、その建物の上に高度付きの軽量3Dアイコンとして表示できる。アイコンは少数の単純形状を再利用し、地図の建物形状や操作を隠さない大きさにする。
- Mapbox由来の地図と、利用者の記録や推定による表示を見分けられるようにする。

3Dアイコンの座標は対象建物の形状中心、高度はMapboxの建物属性にある`height`へ固定する。アイコンから屋根の固定点まで接続線と標的リングを表示し、建物自体も選択色で示す。高さの根拠がない場合は建物上に配置しない。種類、参照先、確認状態は表示データとして分離する。詳細3Dと近距離の広域3Dで表示し、俯瞰や密集時は非表示または集約する。

### 不足するランドマークの補完

Mapboxの標準3D表現に存在しない、または体験上必要な特徴が不足しているランドマークだけを、独自の3Dモデルで補完する。街全体を独自モデルで再制作せず、Mapboxの建物を基盤として利用する。

- 対象は、経路の目印、地域らしさ、場所の記憶、成長演出に必要な建物に限定する。
- Mapboxに十分な3Dランドマークがある場合は重複して制作しない。
- 制作前に、対象地点でのMapbox表示、建物形状、高さ、視認距離を確認する。
- 独自モデルはBlenderで制作し、編集可能な`.blend`とアプリで利用する軽量なglTFまたはGLBを残す。
- 制作にはAstraを利用し、形状、縮尺、原点、向き、材質、ポリゴン数を同じ基準で揃える。
- 地図上でその場所だと分かる実際の外形、屋根、塔、段差などの形状を優先する。

# 「みんなで育てる」要件

更新日：2026年9月8日

**目的や場所から、友人や発信者の体験を見つけ、自分でも試す。** 共有と比較で互いの街の使い方を知り、一緒に出かけるきっかけを作る。

[基礎要件](../spec/requirements.md)の「地図の重ね合わせ」「視点と体験の移し替え」を引き継ぐ。比較と共有はこのタブ、街の探索・経路案内・訪問による成長は[地図を育てる](grow-map.md)で扱う。

## 1. 目的・場所から体験を探す

初期画面は目的・場所の検索を中心に、共有体験と友人一覧を開ける構成とする。人物の指定は不要で、友人がいなくても公開情報を探せる。

| 検索の入口 | 例 | 見つかる情報 |
|---|---|---|
| 目的から | ラーメンを食べたい、服を買いたい、一人で休みたい | 目的に合う場所、体験のコツ、おすすめルート |
| 場所から | 現在地周辺、駅・街の名前、特定の店、地図の表示範囲 | その場所に関する体験や、周辺を巡るルート |
| 目的と場所から | 渋谷で服を買いたい | 指定した地域で目的に合う場所・ルート |

目的・場所は片方だけでも検索でき、後から追加・変更・解除できる。検索対象の地域や現在地の範囲を示し、変更できるようにする。

結果には「何ができるか」「どこか」「誰の体験か」を示す。友人・公開情報・特定の発信者は絞り込みとして使い、結果からその人の共有情報やレンズへ進める。該当なしと取得失敗を区別し、条件を保って変更・再試行できるようにする。

### 友人との接続と共有

友人を探してつながり、関係を解除できる。友人がいない場合は接続の入口を、共有情報がない場合はその状態を示す。

共有情報では、誰が、どの場所で、何をして、なぜそこを選んだかを、写真・意見・体験から読めるようにする。場所の詳細、友人との比較、その人のレンズへの入口を設ける。友人に加え、地域住民などが閲覧を許可した地図も比較対象にできる。

自分の場所・経路・用途・理由・写真・説明・集約した活動範囲は、共有する項目と相手を選び、公開前に確認できる。後から変更・取消でき、友人関係だけで移動軌跡全体を共有しない。

### 地図上で体験を見つける

地図では、現在地・表示地域と目的に合う場所・ルートを、AIへ質問せずに見つけられる。目的は検索・選択で指定し、文脈から提案された場合も変更・解除できる。

| 場面 | 地図で見つかるもの | タップした後 |
|---|---|---|
| ラーメンを食べたい | 近くで友人が以前訪れたラーメン店 | 「にんにく多めが美味しい」など、友人が残した注文のコツや感想を読む |
| 服を買いたい | 友人が共有した買い物ルート | 店を回る順序、各店のおすすめ、所要時間を確認して案内を始める |
| この街を散歩したい | インフルエンサーが公開した街歩きルート | 誰のどんなテーマのルートか、立ち寄り先と説明を確認する |

場所名だけでなく、注文方法・買ったもの・過ごし方など、その人の具体的な体験を共有できるようにする。投稿者、訪問・投稿日、元の言葉を確認でき、個人の感想と店舗の現在の提供情報は区別する。「友人が訪れた」と「友人がおすすめした」も分け、訪問記録だけから好意的な感想を作らない。

### 友人・インフルエンサーのおすすめルート

友人やインフルエンサーが共有・公開したルートを、目的と地域から見つけられるようにする。ルートには作成者、テーマ、立ち寄り先と順序、各地点のおすすめ、所要時間、更新日を持たせる。自分でも場所と順序に説明を付けてルートを作り、共有範囲を選んで公開・更新・取消できる。

ルートは作成者を示し、特定の発信者でも絞り込める。公開ルートは友人関係がなくても閲覧できる。

気になるルートを保存し、「地図を育てる」で詳細と案内を開く。元のルートとAIの変更案、共有された所要時間と現在の検索結果を区別し、変更点を示す。

共有する人・体験・ルートはこのタブで管理する。候補は「地図を育てる」へ渡し、地図からも共有一覧や比較を経由せず直接見つけられる。

## 2. 互いにとっての場所の意味を知る

比較の中心は、**誰が、どんな場面で、その場所を何のために使い、なぜ選ぶか**という関係とする。地図の重ね合わせは、その共通点や違いを確かめる表示方法の一つとして使う。

| 比較すること | 発見の例 |
|---|---|
| 同じ場所の意味 | 「君には友人と話すカフェだけど、僕には一人で勉強する場所なんだね」 |
| 同じ場面での選び方 | 「この駅に来て昼ご飯を食べるとき、僕は定食屋、君はラーメン店に行くんだね」 |
| 別の場所に共通する役割 | 「僕にとっての気持ちを切り替える河川敷は、君でいうとこの本屋なんだね」 |
| 共通する場所と役割 | 「二人とも、この公園で一息ついていたんだね」 |
| 自分になかった使い方 | 「いつも通る建物に、君が休憩する場所があったんだね」 |

### 比較の入口

場所、場面、用途のいずれかから相手との関係を探せるようにする。

- **場所から**：このカフェは、それぞれにとってどんな場所か。
- **場面から**：この駅で昼ご飯を食べるとき、それぞれどこを選ぶか。
- **用途から**：自分が気持ちを切り替えるこの場所に対応する、相手の場所はどこか。

相手・期間・曜日区分・時間帯・同行者などで条件を絞る。同じ建物や施設分類に限らず、異なる場所・地域・業種の間でも、本人の用途と理由から対応を探す。昼食の店が違う場合も、速さ・量・落ち着きなど、なぜ選ぶかを根拠がある範囲で示す。

### 結果の見せ方

比較カードには、共通の場面・役割と、双方の場所・用途・理由・違いを並べる。「同じ駅で昼食」は共通の場面であり、同じ好みと決めつけない。「河川敷と本屋が対応する」場合も、場所全体が同じ意味ではなく、気持ちを切り替える役割で対応すると示す。

カードと地図の選択を連動させ、「自分だけ」「相手だけ」「重ね合わせ」で場所・経路・活動範囲を確認できる。持ち主を明示し、離れた場所や別都市は並列表示・移動で双方を見られるようにする。意味の対応と移動経路は異なる表現にし、名前の類似だけで場所を統合しない。

### 根拠を見て訂正する

AIの比較から、本人の言葉・体験・時間帯・同行者などの根拠を確認できる。AIの解釈と本人の説明を区別し、対応を「合う／違う」で訂正できる。否定した対応を同じ根拠だけで再生成せず、新しい回答があれば訂正を踏まえて見直す。

情報不足は「共通点がない」「相手しか知らない」と断定しない。比較は共有された記録の範囲で行う。

## 3. 友人のレンズと体験を試す

共有や比較から、気になる場所の記憶を読み、その人の視点で街を見る操作へ進める。

| 操作 | 次の体験 |
|---|---|
| この人のレンズで見る | 「地図を育てる」の他人レンズへ移り、共有された用途に応じて注目点や建物の姿が変わる |
| 自分も行ってみる | 対象の場所を目的地にして経路案内を開く |
| この体験を別の街で試す | 元の体験と移し替え先を選び、その役割や順序を保つコースの提案へ進む |

同じカフェが自分には本、友人には吹き出しの建物として見えるなど、用途の違いをレンズの表現にもつなげる。表示するのは共有された視点であり、自分の用途や成長状態を上書きしない。

### 別の街で体験を再現する

元の体験の目的・役割・順序・理由・必須条件を確認し、地域・出発地・時間・歩行距離・移動条件を指定する。「この人の目線で歩く」と「自分向けにアレンジする」を選べるようにする。

結果には、維持した特徴、変更点、再現できない要素、未確認の情報を示す。相手への忠実さと自分への適合を分け、思い出や人との関係をそのまま移せたと扱わない。候補がなければ不足条件を示し、本人が条件を調整する。具体的な候補確認と案内は「地図を育てる」へ引き継ぐ。

## 4. 一緒に出かけるコースを作る

同行する友人を選び、共有された好みと今回の希望からコースを提案する。

| 入力 | 提案で分かること |
|---|---|
| 同行者、それぞれの希望、出発地、使える時間、距離・移動条件 | 各人が楽しめる場所、訪問順序、所要時間、各人の希望を満たす点と調整した点 |

共通の好みだけでなく、違いもコースに活かす。例えば「本屋に寄った後、水辺で休む」など、双方の理由を取り入れる。これは組合せの例であり、実際の候補と移動時間は場所・経路の情報で確かめる。

候補を確認・変更し、選んだコースと同行者条件を「地図を育てる」へ渡す。条件を満たせない場合は不足を説明し、勝手に緩めない。コースの採用と友人への送信は別の操作にする。

## 5. 体験を持ち帰る

友人から教わった場所は、実際に自分が訪れた場所と区別して残す。訪問後は写真・感想・用途を記録し、自分の建物の成長へ反映する。同じ場所でも自分は別の理由で気に入った、という違いを次の比較や提案に使う。元の持ち主の説明は書き換えない。

友人の共有訪問は、「フレンドも行っていたよ」という自動クエストのきっかけにも使う。クエストの表示・受諾・達成は「地図を育てる」、振り返りは「自分を知る」で行う。自分の感想を友人へ返す場合も公開範囲を確認する。

## 6. 保存・共有取消・失敗時

友人関係、共有項目と公開範囲、場所ごとの具体的な体験メモ、作成・保存したおすすめルートと作成者・版、比較相手・条件・双方の根拠と版・訂正、採用した体験やコースを保存する。地図から戻ったときは、比較相手・条件・選択・表示位置を保持する。

共有取消後は、対象情報を共有画面・比較・検索・推薦・クエスト・AIの参照から外し、派生する説明を更新する。保存済み結果や会話を再表示する場合も現在の共有範囲を確認する。

データなしと取得失敗を区別し、失敗時は入力条件や同行者を保って再試行できるようにする。共有解除で比較対象がなくなった場合は、その状態を示して相手を選び直せるようにする。

更新日：2026年9月8日

| 防災マップ | ハザードマップ、冠水状況、避難先と避難経路の案内 | 対象地域の災害リスクと冠水情報を確認し、避難先までの経路を表示する |
| バイクマップ | バイクで走れる場所・道路の表示 | 対象地域で走行できる場所と、確認できる通行条件を地図で探す |
| 聖地マップ | 作品などに関連する場所と説明の表示 | 作品・テーマを選び、関連地点を開いて由来や見どころを確認する |

### 表示する情報

- **防災**：ハザードマップの想定リスクと、時点のある冠水状況を区別する。情報源・対象時刻・更新状況を示し、取得できない地域を冠水なしと扱わない。避難経路は参照した冠水・通行情報と未確認部分を示し、安全が保証された経路として表示しない。
- **バイク**：走行可否の根拠と、分かる範囲の車種・時間帯などの制限を示す。未確認の道路を走行可能と断定しない。対象車種と道路の範囲は詳細設計で決める。
- **聖地**：作品・テーマ、関連地点、関係する説明と出典を示す。デモで扱う作品や地点、画像などの利用条件は素材選定時に確認する。

デモの再生・模擬データと実際に取得した情報は画面で区別する。各プラグインの情報源・対象地域・更新方法は実装前に確定する。

## 3. GitHubの開発ノウハウで、自分でも作る

# 「自分を知る」要件

更新日：2026年9月8日

移動と体験を振り返り、自分が場所をどう使い、なぜ選ぶのかを知る。**記録を見る → 理由を話す → 傾向や変化に気付く → 次の探索に活かす**流れを中心に置く。

[基礎要件](../spec/requirements.md)の対話・用途・理由・訂正の方針を引き継ぐ。初期画面は今日の振り返りとし、日付を選んで過去も見返せる。日記形式は望ましい機能として扱う。

## 1. 今日の移動と訪問を振り返る

日常の記録・欠損や曖昧な区間の補完は[地図を育てる](grow-map.md)で行う。このタブでは、その記録を地図と時系列で振り返る。時刻・滞在・写真・メモ・会話を、場所や経路に結び付けて表示する。

通過、訪問候補、確認済みの訪問を区別し、候補の確認・拒否・別の場所への訂正ができる。記録が欠けた区間を移動済みとして補わず、一部の記録を一日の全行程として見せない。

振り返り中も同じ記録・補完操作を開ける。記録がない日は、場所を選んで手入力や会話から始められる。記録のない訪問も本人の申告から追加でき、昔の記憶と現在の訪問は区別して残す。

## 2. AIと話して、場所の意味を見つける

日付・場所・経路・体験を選び、行動・感想・選んだ理由を話す。AIは記録時の会話も引き継ぎ、回答に応じて質問を変え、用途と理由を整理する。

| 振り返り | 残す内容・次の発見 |
|---|---|
| 「帰宅前に河川敷で一人になっていた」 | 気持ちを切り替える用途と、帰宅前という条件 |
| 「視界が開けるところが好き」 | その場所を選ぶ理由 |
| 「本屋でも気持ちを切り替えている」 | 異なる場所に共通する役割と、視界・本という理由の違い |
| 「おすすめの店はどうだった？」 | 期待に合った点・違った点と、次の提案への手掛かり |

時間帯・天候・同行者・気分などによる違いも扱う。例えば同じカフェでも、一人なら勉強、友人となら会話の場所になり得る。

質問は原則一度に1問とし、答える・後で答える・飛ばすを選べる。回答を誘導せず、既に話した理由を聞き直したり、新しい根拠なしに同じ質問を繰り返したりしない。

### 本人の説明とAIの解釈を分ける

観測された行動、本人の言葉、AIの仮説を区別し、解釈から元の記録や発言を確認できるようにする。毎日通る道でも、好みなのか、通学や時間の制約なのかを記録だけで決めない。本人が語っていない好みや未回答の内容は仮説として扱う。

本人は用途・理由・解釈を確認・訂正・保留できる。「この日は急いでいただけ」と訂正した場合は対象と条件を保存し、休日全般の好みへ広げない。同じ記録を再読込しても、訂正前の解釈へ戻さない。

## 3. 統計と傾向から、自分の変化を知る

週・月・年を切り替え、行動の集計と、場所をまたぐ選び方の傾向を見る。

| 見るもの | 表示例・候補 |
|---|---|
| 行動の統計 | 移動距離、訪問数、新しく訪れた場所、よく行く地域・時間帯 |
| 場所の使い方 | 勉強・交流・休息など、どんな目的で街を使っていたか |
| 選ぶ理由の傾向 | 複数の場所に共通する、落ち着く環境や寄り道の仕方 |
| 時間による変化 | 以前と最近で、行く場所・用途・理由がどう変わったか |

集計期間と記録の欠落を示し、数値とAIの解釈を分ける。傾向には根拠と成立する条件を添え、元の訪問・会話へ戻れるようにする。傾向の生成は、元の実装仕様の既定案では異なる2体験以上を条件とするが、件数だけで好みを確定しない。

好みが変わった場合は、過去の体験を当時の記憶として残し、現在の推薦に使う条件を更新する。統計指標と比較期間の詳細は未決とする。

## 4. パーソナリティ診断

記録や振り返りから、場所選びや過ごし方の特徴を診断する。対象期間と根拠の記録・回答を示し、本人の追加・訂正で見直せるようにする。

情報不足なら無理に分類しない。人物像を固定するラベルだけで地図や推薦を構成せず、実際の用途・理由・条件も使う。診断方式、質問票、分類名、更新時期は未決とする。

## 5. 日記として残す（望ましい機能）

軌跡・訪問・写真・感想・会話を一日の日記にまとめ、保存・追記・編集して読み返せるようにする。AIが文章を作る場合は本人が確認して保存する。

## 6. 発見を地図と次の体験へ返す

| 振り返りで分かったこと | 反映先 |
|---|---|
| 「このカフェは勉強する場所」 | 「地図を育てる」の用途に応じた建物の姿 |
| 好む環境、使える時間、訪問後の感想 | 行き先・経路・自動クエストの提案 |
| 別の場所に共通する用途や選ぶ理由 | 「みんなで育てる」の比較。共有が許可された範囲だけを使う |
| もう一度行きたい場所 | 「地図を育てる」の目的地と経路案内 |

「地図を育てる」から指定された日付・場所・記録で振り返りを開ける。用途の記録と訪問の確認は区別し、会話しただけで建物を訪問済みにしない。会話や日記は自動公開せず、共有する場合は対象と範囲を確認する。

## 7. 保存・失敗時・設定

元の記録と発言、用途・理由・条件、仮説・確認・訂正・保留、根拠、解釈の適用期間、診断結果を保存する。日記を採用する場合は対象日と記録を結び付ける。

プロフィール、公開範囲、通知、位置情報、AI、データ管理、ホームの起動設定は補助的な設定入口にまとめる。
