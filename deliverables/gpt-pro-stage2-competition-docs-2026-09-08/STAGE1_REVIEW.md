# 育てる地図 — 優勝を目指すためのレビューと完成案

2026年9月8日。企画と要件のレビューであり、アプリの実装完了報告ではない。

**結論：全4タブと既存機能を保持し、「場所を選ぶ理由が育ち、他者・他都市へ使える」という一つの体験でつなぐ。診断は、本人が訂正でき、次の選択で確かめられる状況別プロファイルへ具体化する。OpenUASは異都市の地域候補取得へ自然に組み込み、性格や現在の店内状態を推測する道具にしない。**

詳細は `STAGE1_HANDOFF.md` を参照。137件の安定ID付き要件、各受入条件、11の利用シナリオ、7段階の依存順、旧A01〜A55の全件対応、最新6文書の原文を含む。新しい提案は個別承認済みではない。

## 1. 結論：何で勝つ案にするか

### 1.1 製品の一文

> **育てる地図は、「どこへ行ったか」ではなく「そこで何を得て、なぜ選んだか」が育ち、その理解を他の人・他の街でも使える地図。**

利用者向けには「毎日が、自分だけの街になる」。審査員向けには「本人が訂正できる体験の記録を、地図の成長・条件付きの自己理解・体験の移し替え・Codexによる機能拡張で共有する」と説明する。

日常の入口は、講義・仕事帰りの20〜30分の寄り道、よく行く場所の記録、友人からの実用的な体験である。これは検証を始める入口であって、旅行、バイク、聖地巡礼、防災を削るための対象者限定ではない。友人がいなくても自分の記録と公開体験から価値が出る。

### 1.2 現案の強さと弱点

強さは、地図を育てる感覚的な楽しさと、用途・理由・他者の視点という情報の深さが同居していること。自分の建物が姿を変えるだけでなく、その理由が「次にどこへ行くか」を変えると、見た目と実用性が接続する。

弱点は、現状の説明では「3D地図」「日記」「おすすめ」「性格診断」「友人SNS」「プラグイン」が別々のサービスに見えやすいこと、そして診断・移し替えの正しさを文章の自然さで済ませる余地があること。

Googleの公式発表には会話型の場所探しとImmersive Navigationがあり、Fog of Worldには探索記録、Polarstepsには旅行の計画・記録・共有がある[W02, W15, W16]。「AIがおすすめ」「訪問で地図が変化」「3D」「記録を共有」だけを未踏の独自性として売り出すべきではない。各サービスの全機能を網羅比較したわけではなく、本案の世界初を主張しない。

差別化の中心は次の連続動作とする。

**本人の一言 → 根拠付きの用途・理由 → 建物の変化 → 条件付き仮説 → 本人の訂正 → 同じ候補に対する提案の変化 → 他者・他都市の体験 → 実際の感想で更新。**

これを動作と記録で証明することが、汎用チャットへ長いプロンプトを与えるだけのデモとの差になる。個々の手法の発明を主張するのではなく、実際の制約、版、権限、検証を接続したシステムとして価値を示す。

### 1.3 4タブが共有するもの

| タブ | 利用者に見える価値 | 共通する体験データの使い方 |
|---|---|---|
| 地図を育てる | 自分の経験が街の姿と次の行き先になる | 確定訪問は成長、確認した用途は造形、現在の希望は候補選びに使う |
| みんなで育てる | 同じ場所の違う使い方、違う街の似た体験を発見する | 許可された用途・理由・順序を比較し、体験レシピとして移す |
| アプリを育てる | 必要になった判断・表示を追加する | 同じ根拠・権限・経路の契約の上へプラグインを追加する |
| 自分を知る | 自分が何を優先するかを、根拠と反例から知る | 記録を診断の材料にし、訂正を全体へ戻す |

AIチャットを4つ作るのではなく、記録と訂正は一度行えば各画面へ反映される。一方、用途の変更・訪問の変更・好みの変更は別の操作であり、訂正が無関係な情報まで壊してはならない。

## 2. 「占いではない診断」の具体案

### 2.1 診断を撤去せず、出力する命題を変える

「あなたは内向型」「冒険家タイプ」ではなく、**「平日の帰宅前、一人で時間が少ない場面では、遠い新規店より、寄り道の短さと落ち着けることを優先しやすい」**という条件付きの命題を扱う。

画面の名称は「街との付き合い方」。補足として「状況別の行動パーソナリティ」を使える。これは新しい心理検査が科学的に妥当と証明されたという意味ではない。既存研究には、性格に関連する行動の状況依存性や個人内変動を扱うものがあるが、それだけで位置ログから性格を診断できることにはならない[W10]。

画面には、本人が言ったこと、観測できたこと、モデルの仮説、反例・別の説明、次に確かめたいことを分けて示す。2体験から仮説を作ることはできても、2体験で傾向が検証済みとは言わない。

### 2.2 学習するのは「選べたとき、何を優先したか」

通学先に100回行ったことは、その場所を100回自由に選んだという意味ではない。未訪問の店も、知らなかった・閉店していた・高かった・その日は時間がなかった可能性がある。推薦ログの選択バイアスは既存研究でも問題とされている[W12]。

保存する単位は、状況、表示した候補集合、各候補の実行可能条件、選択・見送り、本人の理由、体験後に目的に合ったかである。出せなかった候補や見ていない候補を「嫌い」として学習しない。

初期実装は、巨大な独自学習モデルではなく、少数の属性と状況との交互作用を持つ正則化二者選択モデルを推奨する。数式は実装方針の例であり、最終のモデル・推定法はStage2でテストして定める。

\[
P(a\succ b\mid u,c)=\sigma\{w_u^\top[\phi(a,c)-\phi(b,c)]\}
\]

`c`は平日/休日・時間・同行者・予定・明示された現在の希望等、`φ`は移動増分・追加費用・既知/新規・本人が確認した環境などである。利用可能な選択肢だけが比較対象となる。静けさ等の根拠がない属性に想像の値を入れない。

初期の事前分布や正則化は推定を安定させるための仮定であり、精度保証ではない。申告から始め、二者選択と結果から更新し、小標本では不確実性を残す。場面ごとに変わる状態を、長期的な傾向に全部吸収させない。冷開始は明示条件に基づく推薦で成立させ、学習データが貯まるまで利用をロックしない。

文脈に応じて選択し結果から更新する推薦はcontextual bandit研究と接続できる[W11]。ただし、本製品で何を報酬にするかは独自の設計であり、クリック率や移動距離を最大化するのではなく「本人がその場面で望んだ体験への適合」を優先する。探索のために危険・費用・同意の制約を緩めない。

### 2.3 診断が機能していると見せる操作

例：AIが「静かさを優先している可能性」を提案する。本人は「この日は時間がなかっただけ」と訂正する。

その結果、当該体験を静かさの支持証拠から外し、候補集合を固定した次の推薦の順位と理由を再計算する。既に本人が確認した訪問や「勉強した」という用途は変えない。別途用途も訂正した場合だけ、該当建物の造形を更新する。

これにより「自分の説明が修正できる」だけでなく「誤った理解が次の行動へ残らない」ことを示せる。推薦候補自体を同時に入れ替えると訂正の効果が分からないため、デモでは同じ候補集合を用いる。

### 2.4 質問と小さな検証

毎回長い質問票を出さず、対立する説明を分ける一問を出す。例えば「同じくらいの距離なら、静かな場所と、新しい発見がありそうな場所のどちらに寄りたい？」。どちらも行ける条件でなければ有効な比較とはしない。

情報利得を用いる質問選択は追加する価値があるが、実装の初手は明確な競合仮説に対するルール選択でよい。後に同じ契約の中で事後分布に基づく選択へ進める。質問の少なさ、辞退可能性、機微性を一緒に評価する。

希望者が次回の別場面で試し、その結果を仮説へ戻す。「当たっている気がする」という自己申告だけを精度と呼ばず、別場面での選択・結果・外れた事例を記録する。これは自己理解の補助であって、臨床的・因果的な効果の証明ではない。

## 3. 体験の移し替えとArea2Vec/OpenUAS

### 3.1 体験レシピ

「この店と似た店を探す」ではなく、体験を次の構造で持つ。

| 要素 | 説明例（架空の体験） |
|---|---|
| 目的 | 帰宅前に気分を切り替える |
| 役割の列 | 本屋で新しい話題に触れる → 視界が開けた場所で一息つく |
| 順序・遷移 | 刺激を受け取ったあと、余白のある場所へ出る |
| 理由 | 本に囲まれる感じ／空が見えること |
| 必須条件 | 到着期限、追加費用、歩行上限、座席が必要ならその確認 |
| 変更可能なもの | 店名、建物、移動手段の一部 |
| 移せないもの | そのときの友人との会話、個人的な思い出 |

AIはこの構造の抽出と説明を担う。候補取得、順序、時間・料金・道路・営業条件は独立に検証する。これを「体験コンパイラ」と呼んでもよいが、検証できるのは構造・データ・制約であり、主観的に同じ気持ちになることを形式的に証明するものではない。

「相手の体験に忠実」「自分の条件に合う」を別軸にして比較し、保存した・変えた・再現できない・まだ不明を明細にする。見かけだけの再現率ではなく、利用者が変更内容を選べることに価値を置く。

### 3.2 OpenUASを置くのは、地域候補の取得部分

OpenUASは都市の滞在に基づく地域利用の埋込みを公開しており、異都市比較のためのアンカーを持つ。公開説明の対象は東京、大阪、名古屋、札幌、福岡、仙台、広島、京都の8都市である[W03, W04]。

採用案は、元体験が持つ地域利用の特徴から、別都市で類似する地域を候補に含め、その地域内で実際の施設・用途・現在条件を調べることである。カテゴリ検索、地域情報からの検索、UAS類似検索を併用し、UASが適さない体験や都市でも本体は同じ処理で動く。

UASを入れるだけで推薦がよくなるとは言えない。比較可能なモデル版であることを確認し、UASなしとの候補取得比較を行う。地域取得の効果を見るため、この評価では同じ候補集合に固定せず、同じ探索対象・検索予算を用いる。診断訂正の評価で候補を固定することとは目的が違う。

### 3.3 やってはいけない結び付け

地域ベクトルから「内向的な人の街」「この店は静か」「ここは今空いている」と断定しない。意味を学習していない潜在次元に、静けさ等の名前を勝手に付けない。個人の選好モデル、文章埋込み、UASベクトルを同じ空間とみなして内積しない。

公開データには過去の期間が使われ、50mメッシュの一部には250mから補完したものがある。`is_complemented`と元の解像度・時期を保持する[W03, W04]。席、騒音、店の営業、今日の混雑、災害時の通行は別の出典か本人の確認を必要とする。

### 3.4 地域と権利の判断

最初に実際の収録と経路を確認する比較地域は、既存試作を生かす名古屋と、公式都市一覧にある東京を推奨する。横浜は開催地・既存地図の候補として保持するが、公開の8都市名一覧だけから横浜の厳密なメッシュ収録有無を断定しない。横浜・箱根の体験にもUASがあると偽らず、実収録が確認できた範囲で有効化する。

公開説明はArea2Vecに関する特許と商用時の連絡先を案内している[W03]。オープンデータという名前から商用・再配布無制限と判断しない。コンペ利用、切出しデータの同梱、モデル・コード、将来商用を分けて確認する。

### 3.5 3D人流研究とのもう一つの接点

同じ建物の地下の交流場所と上層階の作業場所を別の場所として扱う「同じ建物、違う意味」は、元要件の階・入口の区別を生かす自然な追加体験である。2Dの見栄えを3Dへ変えるだけでなく、同じ平面位置にある異なる用途を混ぜない価値になる。

高度付きの研究資産を使う場合も、既存モデルが本ZIPにある・自由に配布できる・階を正確に識別できるとは仮定しない。高さ帯と階番号を区別し、本人確認やデータ出典と併用する。PLATEAU全面導入を再度依存条件にする提案ではない。

## 5. 実現可能性：何が既知で、何が未検証か

**技術的な経路はあるが、現時点で全機能の当日完成を保証できる状態ではない。** 特に外部契約・データ範囲・描画差替え・任意コード隔離は、人数を増やしたり最後に頑張ったりするだけでは解決しない。これらをG0へ出し、他の実装と並行して潰す。

| 対象 | 成立の見通し | 外部確認/未確認 | 先に通す検査 |
|---|---|---|---|
| 根拠付き体験、訂正、比較 | 既存設計に保存・版の骨格があり、通常のアプリ実装として具体化可能 | 本ZIPにDB/API実装なし | 1体験の保存→訂正→派生失効が再現する |
| 条件付きプロファイル | 少数属性の推定と質問選択で始められる | 対象者での有効性・学習データ未検証 | 合成の明確な選択差＋未使用場面の評価 |
| 象徴建物への置換 | Mapbox公式にStandardの建物をclipで消し独自モデルへ替える例がある[W05] | 実験的機能。密集街区・複合建物・対象版での確実性は未検証 | 1棟置換、隣棟保持、原形復帰、30fps目標の実測 |
| OpenUAS候補取得 | 公開データ・モデルと異都市比較の設計がある[W03–04] | 正確な地域メッシュ、モデル整合、権利、推薦改善は未検証 | 対象2地域のデータ確認と同予算の候補比較 |
| 徒歩経路 | Mapbox等に歩行経路APIがある[W07]。旧設計ではopenrouteserviceを候補とした | 最終プロバイダー・契約・地域の歩道/階段等は未選定 | 実道路接続、到達不能、逸脱、階段条件 |
| 交通・定期運賃 | 駅すぱあととNAVITIMEには定期区間を考慮する資料がある[W08–09] | 駅すぱあとの当該定期控除は鉄道のみ。バス含む全券種や契約は未確認 | 対象券種ごとの小さな実リクエストと期待値照合 |
| ストアと3プラグイン | manifest・権限・導入版を共通化できる | 各プラグイン用の実データ・更新・CORS・利用権は別問題 | 3種それぞれの入力→出力を共通契約で通す |
| 新規コード実行 | Codexからの生成・イベント・承認は公式に扱える[W13–14] | Codexのsandboxと配布プラグインのsandboxは別物。後者は未実装 | 無限ループ、無断通信、親DOM、過大出力の負例 |
| 防災・バイク | 根拠と不明を保持した情報提示は設計可能 | 災害中の安全・車種別全道路通行を保証できるデータは未確保 | データがない場合に危険な断定をしないこと |
| 端末背景記録 | 原案どおり実機段階で既存SDK接続を検討 | Safariデモは背景測位・省電力・ストア審査を証明しない | 実機の権限・復帰・電池・継続記録試験はG6 |

Mapbox Directionsだけで日本の鉄道・バス時刻表と定期運賃まで作る想定は置かない[W07]。ルーティング層を歩行・公共交通・車種別制約へ分け、プロバイダーごとの対応範囲を可視化する。「無料ルート」や「走れる道」という表現は、確認できた条件内に限る。

外部から静けさや座席が確認できない施設について、LLMに調べたふりをさせない。本人の過去体験、公式情報、利用可能な現地データ等のどれが根拠かを示す。過去体験を現在保証に読み替えない。

## 9. 工程：機能を落とさず、依存関係で順序を決める

### 9.1 全体工程

| 工程 | 完成させるもの | 終了判定 | 並行して進めること |
|---|---|---|---|
| G0 成立性と環境 | 大会の既存資産確認、API認証/券種、建物置換、UAS実収録/権利、端末コード隔離、Simulator | それぞれの小さな実試験で外部条件と技術上の入口が確認される | 素材の出典整理、3プラグインの情報源調査、基本契約 |
| G1 共通基盤 | 4タブ、利用者境界、記録/原文保存、ID/版、訂正/取消、ジョブ | 1件の保存→読込→訂正→派生失効、履歴なし利用 | 地図造形、交通接続、プラグイン実行基盤 |
| G2 一人の価値 | 建物本体の変化、人物挙動、振り返り、条件付きプロファイル、一問、クエスト | 本人の一言が地図と次候補へ反映。訂正を再起動しても保持 | 写真/日記、共同比較の検索、地域候補取得 |
| G3 人・都市・移動 | 比較全類型、共有、体験レシピ、UAS候補、定期/公共交通、共同コース、感想 | 元体験→他都市の成立した候補→自分の感想→再推薦 | 階比較、他者意見、体験返信、プラグイン統合 |
| G4 拡張と修復 | ストア、3種すべて、新規コード生成/独立検証/導入、5形式取込み、修復 | 3種の導入→利用と作者以外による新規機能作成、列名復旧/意味変更保留 | 差分証跡・再現ガイド・負例試験 |
| G5 全体の証明 | 全要件の受入、A01〜55、新規受入、実API、Simulator、性能、通しピッチ | 状態・ログ・保存版から成功が追え、未達が隠れない | 審査用短縮実演、詳細実演、再現資料 |
| G6 従来からの次段階 | 実機背景記録、ネイティブ包装、認証付き一般公開、終了中通知、配布、アプリ内制作UI | 実機/権限/電池/配布要件を別途合格 | 長期的なモデル検証・地域展開 |

G4の実装をG3が終わってから始めるという意味ではない。**G0でランタイムを検証し、G1から契約に沿って並行開発し、G4で全体へ統合する。** 交通も同様にG0から実接続を調べる。

4人チームの場合の推奨分担は、地図・操作、共通データ・自己理解、比較・移し替え・交通、プラグイン・Codex・情報源。人数は未確認であり、4人が確保済みとはしない。2人の場合は同じ仕事を2系統に束ねるが、工数が半分になるとは考えない。

### 9.2 大会までと当日の区別

公式ルールは2026年9月15日9:00〜21:00の公式開発期間に実質的に開発することと、重要な既存資産の書面開示を求める[W01]。この時間全てがコーディングに使えるとは限らず、第1段階の提出締切・ピッチ時間は別に確認する。

事前は設計、契約調査、環境、入力候補、利用権、既存資産の開示内容を整理する。事前PoCや試作コードを本番へどこまで持ち込めるかは主催者の明示条件を確認し、許可されていない再利用を前提に工程を短縮しない。

当日は最初の作業時間帯でG1と各トラックの最小接続を合わせ、途中で一度「記録→意味→地図」の通し動作を合流させる。その後もトラック単体完成を待たず、同じデータ契約へ小刻みに統合する。最後の枠はピッチ作成だけでなく全体受入と負例の修正に確保する。

G0の検証が失敗した場合は、条件を満たす実装方式・プロバイダーを比較して切り替える。機能を消したり、実APIを保存済み表示で偽装したりして工程を完了にしない。未確保の外部条件を残したまま、全量が当日完成すると約束しない。

## 10. 審査に対する見せ方

### 10.1 審査基準との対応

公式の第1段階はCodex活用、実世界へのインパクト、再利用・展開、デモ/ピッチ、参加者投票の考慮が各20%。最終段階は投票以外の4軸が各25%。同点時はCodex活用、次いで実世界へのインパクトで判断される[W01]。

| 軸 | 見せる証拠 | 避ける説明 |
|---|---|---|
| Codex活用 | 新規機能の要求→差分→独立テスト→実行、壊れた情報源の修復、当日の開発履歴 | 「何万行書かせた」「ほぼAIで作った」だけ |
| 実世界へのインパクト | 時間・追加費用・理由に合う具体的寄り道、他者の使い方の発見、訂正の反映 | 根拠のない社会課題の巨大化、災害時安全の断定 |
| 再利用・展開 | 共通の体験レシピ、地域manifest、3種の拡張、第三者が作れるガイドとテスト | GitHubリンクがあるだけで再現できるとする |
| デモ/ピッチ | 一言で街が変わる、訂正で候補が変わる、別都市へ意味が残る | 全画面を順にクリックして終わる |
| 参加者への伝わりやすさ | 自分の「ここをこう使う」に置き換えられる短い体験 | 研究名と安全機構の説明から始める |

### 10.2 短い主実演と完全実演

発表時間が未確定なので、以下は**3分版の仮構成**。公式の時間制限ではない。全機能の完成・実演要件を3分に押し込めて緩める趣旨ではなく、詳細デモ・操作可能状態・検証記録も用意する。

| 目安 | 主実演 | 見せる変化 |
|---|---|---|
| 0:00–0:20 | 「同じカフェでも、私には作業場、友人には話す場所」 | 場所のカテゴリでは表せない違い |
| 0:20–0:45 | 一言記録→3Dで象徴建物へ | 自分の経験が街の形になる |
| 0:45–1:15 | 「静かだからではなく時間がなかった」と訂正 | 同じ候補の順位が変わり、理解を直せる |
| 1:15–1:55 | 友人の体験レシピを別都市へ | UASによる地域候補と、役割/順序/条件が残る |
| 1:55–2:25 | Codexが作った新しい計算の差分・テスト・導入・実行 | 既存3種の切替だけではない拡張性 |
| 2:25–2:45 | 実際の感想を戻す | 地図・自己理解・次の行き先が一つにつながる |
| 2:45–3:00 | 第三者再現と3種の導入済み機能を示して締める | 展開可能性と完成範囲 |

3種すべての「インストール→利用」は詳細実演でそれぞれ通し、単に導入済みアイコンを映したことを受入合格にしない。新規コードの生成が発表尺を超える場合、会場内で実行して得たログ・成果物とその場の実行を区別して示す。生成動画をライブ生成と称さない。

ピッチの締め：

> 私たちが育てるのは、訪問数ではありません。なぜその場所を選び、そこで何を得たかという理解です。その理解が自分の街を変え、他人の体験を使えるようにし、知らない街へ持ち運べます。そして必要な機能そのものもCodexで育てられます。

### 10.3 追加の検証計画

大会前後に行う小規模な試用は、例えば8〜12人・各4〜6場面から始める。人数は研究上十分とする基準ではなく、募集可能性を確認するための計画仮定である。短期の試用で人格診断の妥当性や長期継続率を証明しない。

評価は、初回完了、質問負担、目的適合、移し替えの忠実さと受け手適合、未使用場面の予測、訂正の維持、制約違反、プラグイン第三者再現を分ける。順序効果を抑えるため方法の提示順を入れ替え、どの方式か伏せられる評価は伏せる。人数・場面数・除外理由・失敗も報告する。同じ参加者の多数の選択を独立した多数人の証拠と扱わない。

OpenUASの追加効果が確認できなければ「研究資産だから優れる」と売り出さない。機能を消すのでなく、どの条件で役立ち、どこで根拠が足りないかを可視化し、取得方法を改良する。
