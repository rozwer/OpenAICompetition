# レビュー反映後の要件と受入条件

更新日：2026年9月8日

ユーザーの「良い案だと思います。反映して議論をしましょう」という依頼に基づき、GPT ProのStage1案を今後の要件の基準へ取り込んだ。方針と具体化を続ける点は[反映方針と議論](review-integration.md)に整理する。実装完了や外部条件の確認を意味しない。

本書をID付き要件・受入条件の正本とする。タブ別文書は体験の説明と具体例を持つ。衝突時は本書を優先し、未決の数値・方式は仮定のまま扱う。「由来」は取込元での分類であり、現在の採用状態とは別である。取込元の「今回の追加・変更提案」は今回の反映で方針採用とし、推奨地域・モデル・数値・技術方式の個別確定までは含めない。

元の[STAGE1_HANDOFF.md](../archive/gpt-pro-stage1-2026-09-08/STAGE1_HANDOFF.md)と[requirements.json](../archive/gpt-pro-stage1-2026-09-08/requirements.json)は原本として保全する。今後の改訂は本書で行い、原本を更新する必要はない。出典の略号は元文書の0.1節を参照。

必須/望ましい/将来は要件の範囲、G0〜G6は依存順であり別軸。G0は成立性、G1は共通基盤、G2は一人の価値、G3は人・都市・移動、G4は拡張と修復、G5は通し検証、G6は実機・配布等の後続段階。工程の後ろにある機能を削除した扱いにしない。

2026-09-08追記：独立したセレンディピティ実験の接続案を取り込み、元137件にDISC-001〜008を追加した。全145件。提示は自分で開く操作を基本に余裕があるときだけ提案し、その場の見方と知的関心の変化を中心とする。本人が探索を選んだ場面では苦手な分野も含める。余裕の判定方法などの詳細は次の設計で定める。

## CORE：製品の共通原則

<a id="core-001"></a>

### CORE-001 製品の目的

重要度：必須 ／ 工程：G1 ／ 由来：今回の追加・変更提案  
出典：CONTEXT／R全体

場所の収集だけでなく、状況・用途・理由・結果を本人が育て、その理解を自分の地図、他者との比較、別都市の行動、機能追加に再利用できる製品とする。全4タブを同じ体験と根拠の参照でつなぐ。

**受入条件**：同一の体験IDから、建物の表示・条件付きプロファイル・比較・移し替え・感想へ追跡できる。

<a id="core-002"></a>

### CORE-002 初回から一人で成立

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R地図§1／R一緒§1／R自己§1–2

位置履歴・友人・長期学習がなくても、場所の選択と一言から体験を保存できる。公開情報の閲覧、通常の経路案内も使える。個人化の不足を架空の履歴で埋めない。

**受入条件**：履歴なし・友人なし・位置権限なしのアカウントで、体験保存と公開体験検索が完了する。

<a id="core-003"></a>

### CORE-003 4つの成長を分離

重要度：必須 ／ 工程：G1 ／ 由来：今回の追加・変更提案  
出典：R地図§2／R自己§3–4／Rアプリ

訪問による造形の成長、本人の説明による意味の成長、検証された予測の成長、導入機能の成長を別の状態として扱う。活動量の多さを人間としての成長に換算しない。

**受入条件**：訪問数だけ増えても好き・性格・診断確信度が自動上昇しない。

<a id="core-004"></a>

### CORE-004 重要度と実装順の分離

重要度：必須 ／ 工程：G0 ／ 由来：既存要件  
出典：01_PROMPT／今回ユーザー指示

既存の必須機能を削らずG0〜G5の完成対象とする。望ましい機能と従来から将来だった実機配布等を区別する。工程の後ろに置くことを機能撤回や成功扱いの緩和に使わない。

**受入条件**：全既存要件にID・工程・受入条件が対応し、未完了項目は未完了のまま確認できる。

<a id="core-005"></a>

### CORE-005 事実と実演の誠実性

重要度：必須 ／ 工程：G0 ／ 由来：既存要件  
出典：S実装§1／Sデータ§9–10／A52・55

本人申告・実測・公開情報・合成入力・AI仮説を区別し、実API・入力再生・保存済み結果も別に記録する。保存済み映像や計算結果を今回の生成・実測成功と説明しない。

**受入条件**：表示レイヤーやジョブごとに入力由来と実行方式を確認できる。

## NAV：画面と起動

<a id="nav-001"></a>

### NAV-001 4タブの順序

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R画面§4タブ

下部タブは「地図を育てる」「みんなで育てる」「アプリを育てる」「自分を知る」の順序とする。ホームとAIを独立した第5・第6タブにしない。

**受入条件**：全主要画面で順序が一致し、主要機能が4タブ内から到達できる。

<a id="nav-002"></a>

### NAV-002 起動とホーム

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R画面§起動

ホームの起動時表示は設定で切替え、既定ONとする。OFFなら自分レンズ・2Dの地図へ入る。ホームには今日の再開先、記録、提案を置き、強制的な診断を入口にしない。

**受入条件**：ON/OFFを保存し、再起動後も意図した入口と既定表示になる。

<a id="nav-003"></a>

### NAV-003 レンズと次元の独立

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§1／付録モード

自分・友人・ペルソナのレンズと、2D/3Dの次元を独立して切り替える。友人の情報は共有許可内に限り、架空ペルソナは実人物の発言と区別する。

**受入条件**：自分2D→友人2D→友人3D→自分3Dの全遷移で個人記録が変わらない。

<a id="nav-004"></a>

### NAV-004 意図した3D切替

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図付録モード

2Dから明示的に3Dへ移り、場所タップや単なるズームで勝手に3D化しない。3Dでは人物中心の表現を使い、2Dへ戻ると以前の範囲を復元する。

**受入条件**：施設を選んでも2Dのまま詳細が開き、戻った際に元の2Dカメラが復元される。

<a id="nav-005"></a>

### NAV-005 タブをまたぐ文脈

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R画面§引継ぎ／S実装§4

場所・体験・比較・経路・人物・期間・レンズ・カメラ・入力下書きを引き継ぐ。タブ切替やレンズ変更で進行中の案内を暗黙に置換しない。

**受入条件**：各タブ往復で対象が一致し、案内停止・経路置換は明示操作でのみ起こる。

<a id="nav-006"></a>

### NAV-006 AIの参照範囲

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R画面§AI

AIは現在の対象と参照範囲を表示し、変更・解除できる。送信時に対象と版を固定し、送信後に別の場所へ移っても回答を新しい場所へ誤適用しない。

**受入条件**：場所Aへ送信後Bへ移動してもAに保存され、参照解除後は私有履歴を自動追加しない。

<a id="nav-007"></a>

### NAV-007 AIなしの操作

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R画面§AI／R地図§1・4

訪問記録、用途の手入力、写真、通常の検索・経路案内、共有の管理はAI会話なしで実行できる。

**受入条件**：AI未接続・応答失敗時にも非AI操作と入力保存が完了する。

<a id="nav-008"></a>

### NAV-008 画面サイズと状態

重要度：必須 ／ 工程：G5 ／ 由来：既存設計案を継承  
出典：S実装§4・15／A53–54

390×844 CSS pxを基準に、半面・全画面パネル、入力時のキーボード回避、大画面の左右比較を設計する。色だけで不明・失敗を表さず、動きを減らす設定を提供する。

**受入条件**：iOS Simulator Safariで入力・スクロール・戻る・選択が通り、色を見なくても状態が読める。

<a id="nav-009"></a>

### NAV-009 設定と通知

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R画面／R地図§3／R自己§7

ホーム、位置記録、共有、クエスト、動き、導入済み機能の設定は「自分を知る」からも管理する。質問や探索の通知を停止しても通常利用を妨げない。

**受入条件**：設定への到達が一貫し、OFFの通知が再開・別タブで復活しない。

## REC：記録と本人の説明

<a id="rec-001"></a>

### REC-001 観測・候補・訪問・体験

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：CONTEXT／R地図§1／R自己§1

位置観測と訪問候補と確定訪問と本人の体験を分離する。写真・経路の通過・検索閲覧だけで訪問を確定しない。本人申告の体験はGPSなしでも持てる。

**受入条件**：駅前を通過したログで店の訪問数が増えず、手動の過去体験は記録できる。

<a id="rec-002"></a>

### REC-002 今ここ・過去の手動登録

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R地図§1／R自己§1

「今ここにいる」、地図タップ、候補選択、施設検索、短い自然文で登録・修正する。今の位置と過去日の体験を混同しない。

**受入条件**：現在地点を動かさずに別日の場所を編集でき、候補外施設への修正も可能。

<a id="rec-003"></a>

### REC-003 欠測と概略の保持

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R地図§1／R自己§1／A04

不明区間、精度不良、日時や滞在時間の不明を保持する。「この辺」「昼頃」を偽の秒精度や正確な道路線へ変換しない。分からない・後でを許す。

**受入条件**：欠測区間は切れたまま示し、入力がない一日全体の軌跡を描かない。

<a id="rec-004"></a>

### REC-004 候補の確認・拒否・訂正

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R地図§1／A05–06

位置から複数の候補を作れても本人の明示根拠で確定する。施設・日時・階を訂正でき、却下を保持する。短時間訪問の手動追加も可能とする。

**受入条件**：同一建物内の候補が複数なら自動確定せず、却下後の再生で同じ訪問が復活しない。

<a id="rec-005"></a>

### REC-005 一度だけ保存

重要度：必須 ／ 工程：G1 ／ 由来：既存設計案を継承  
出典：S実装§5／A02–03

入力元と元記録IDで観測の重複を防ぎ、受信順ではなく観測時刻で構成する。手動登録と観測由来候補が重複した場合は本人確認または明確な同一性で統合する。

**受入条件**：同じ入力の再送で観測数・訪問数・造形段階が増えない。

<a id="rec-006"></a>

### REC-006 用途と理由と条件

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：CONTEXT／R自己§2

施設種別、何をしたかという用途、なぜそこで行ったかという理由、時間・同行者・目的・移動制約を別に保存する。本人の原文を残す。

**受入条件**：カフェの「勉強」と「友人との会話」が共存し、カテゴリだけで同一用途にされない。

<a id="rec-007"></a>

### REC-007 確認は原則1問

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§1／R自己§2／A10

記録後の確認は原則1問で、回答なしでも保存を完了する。回答済み・後で・飛ばすを保持し、同じ根拠だけでは聞き直さない。

**受入条件**：一言保存後に画面を離れても記録が残り、再入場で同じ質問を強制しない。

<a id="rec-008"></a>

### REC-008 原文とAIの分離

重要度：必須 ／ 工程：G1 ／ 由来：既存要件  
出典：R自己§2／A08・12

原文を先に保存し、AI抽出は発言内の説明と追加仮説を区別する。AI出力のSchemaだけでなく、参照ID・公開可能項目・否定文・訂正範囲を検査する。

**受入条件**：「好きではなく近かった」を好きと確定せず、途中出力や失敗時に関係を重複保存しない。

<a id="rec-009"></a>

### REC-009 写真の撮影・投稿

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§5／A07

撮影、場所選択、文章、公開先確認、保存・投稿取消を用意する。位置不明は手動で補い、写真に写った施設への訪問を自動確定しない。

**受入条件**：撮影取消で投稿がなく、共有前に公開される画像・文章・場所が確認できる。

<a id="rec-010"></a>

### REC-010 移動モード別の品質

重要度：必須 ／ 工程：G1 ／ 由来：今回の追加・変更提案  
出典：S実装§5の修正／R地図§4

従来の12m/s等の分断値は歩行再生向け設計値として扱い、鉄道・バイクに一律適用しない。移動モード不明時は品質不明を保ち、道路への補正結果も観測そのものと分ける。

**受入条件**：正当な列車ログを全破棄せず、徒歩の瞬間移動は分断でき、使用設定版が残る。

<a id="rec-011"></a>

### REC-011 記録の削除と復元範囲

重要度：必須 ／ 工程：G1 ／ 由来：今回の追加・変更提案  
出典：R地図§6／R自己§7／S実装§13

訪問・理由・写真を削除したら派生表示や学習材料から除き、再計算する。訂正履歴の保持と、本人による削除要求は別処理とし、永続履歴という理由で削除を無効化しない。

**受入条件**：削除した体験が再推薦・検索・診断根拠に残らず、合法的保持が必要なものは別途明示する。

## MAP：地図と成長

<a id="map-001"></a>

### MAP-001 共通地図の実用性

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§1／付録技術

Mapbox Standardを基本に道路・水域・主要施設・必要なラベル・現在精度・案内線を読めるようにする。固定街区制限は製品全域へ適用せず、必要な都市へ移動できる。

**受入条件**：施設探しと案内で名称が読め、名古屋から別都市へ切り替えられる。

<a id="map-002"></a>

### MAP-002 訪問で建物が立つ

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§2

確定訪問によって訪問した建物が立ち上がる。背景を含む現実地図と経験の印を分離し、周囲の建物を訪問済みにしない。

**受入条件**：確認前後で対象建物だけの状態が変わり、友人レンズの閲覧で自分の建物が育たない。

<a id="map-003"></a>

### MAP-003 用途で建物自体を変形

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§2

本人が確認した用途に応じて、学びは本、交流は吹き出し、休息は庭などの象徴的な建物へ置換する。屋根の小アイコン追加だけで本要件を完了としない。複数用途を保持し表示対象を選べる。

**受入条件**：同じ建物に用途を変えて本体形状の変化を確認できる。

<a id="map-004"></a>

### MAP-004 再訪の造形段階

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§2

確定訪問数をもとに造形・装飾が段階的に育つ。5段階の参考は形状の参考であり、好きの強さとはしない。段階境界は可変設定とし、訂正や削除で再計算する。

**受入条件**：用途修正だけでは訪問回数が消えず、重複入力でも段階が増えない。

<a id="map-005"></a>

### MAP-005 好きと成長の語彙

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：R地図§2参考画像

回数で「お気に入り」「特別な場所」を自動付与しない。回数由来の段階名は中立な造形名とし、お気に入りは本人の明示操作・説明に基づく独立属性にする。

**受入条件**：通学・勤務先への頻回訪問だけで好きと表示されない。

<a id="map-006"></a>

### MAP-006 現実形状への復帰

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§2／S実装§9／A13

現実の形状・高さと、自分の象徴的な造形を別データとして切替える。象徴表現を実測高さと称さず、原形へ戻しても記録は失わない。

**受入条件**：現実表示に戻ると出典の高さが復元し、記憶を消さずに象徴表現を解除できる。

<a id="map-007"></a>

### MAP-007 高さ・階の根拠

重要度：必須 ／ 工程：G3 ／ 由来：既存設計案を継承  
出典：S実装§9／A14–15

出典のある高さを使い、不明なら未確認と表示する。地下・上層階の施設、訪問階、階形状、入口・階段・エレベーターの接続を別の根拠で持つ。階数×定数を実測高さとしない。

**受入条件**：建物訪問だけ確認・階不明・入口だけ確認を区別し、接続不明の屋内経路を確定しない。

<a id="map-008"></a>

### MAP-008 人物の現在地表現

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図付録現在地

シンプルで中立的な人物を用いる。移動が確認できる間だけ歩き、停止時は待機する。測位ぶれで歩かず、向きが不明なら向きを捏造しない。初期の着せ替え選択は対象にしない。

**受入条件**：停止入力で歩行ループが止まり、位置精度円と向き不明の状態が分かる。

<a id="map-009"></a>

### MAP-009 地図と同じ3D座標

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：試作src/main.js／R地図付録

人物・象徴建物・屋根表示の位置、縮尺、遮蔽を地図のカメラ座標と一致させる。独立DOMキャンバスの見た目だけを世界座標で動く実装と称さない。

## ROUTE：探索と案内

<a id="route-001"></a>

### ROUTE-001 自動クエスト

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§3

AIへの質問を待たず、本人の目的・条件、定期区間、許可された友人の実訪問、新規性から候補を出す。理由、所要時間・距離、既知の追加費用、成立条件をカードに示す。

**受入条件**：会話していない状態でも根拠付き候補が現れ、未知の費用は0円と表示されない。

<a id="route-002"></a>

### ROUTE-002 押し付けないクエスト

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R地図§3

保存・後で・拒否・停止を用意し、直ちに再提示しない。実際の訪問を確認して完了し、保存・クリック・近接だけで達成としない。

**受入条件**：拒否・停止が再起動後も有効で、候補保存だけでは訪問数が増えない。

<a id="route-003"></a>

### ROUTE-003 歩行案内

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R地図§4

出発・目的地・経由地を指定し、開始、停止、曲がり案内、経路逸脱後の再検索を提供する。観測線・計算経路・比較線を区別する。

**受入条件**：実経路結果で案内でき、API失敗時に直線を歩道案内として出さない。

<a id="route-004"></a>

### ROUTE-004 公共交通案内

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R地図§4

鉄道・バス・徒歩を組み合わせ、出発/到着指定、乗換、事業者、時刻、徒歩接続、運賃を実データで示す。最速と最安を区別する。

**受入条件**：鉄道＋バス＋徒歩の検証ケースで時刻と運賃の取得元を確認できる。

<a id="route-005"></a>

### ROUTE-005 定期券の登録

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R地図§3–4

区間・事業者・経由・有効期間・対象券種を登録し、検索時に有効なものだけ適用する。名称だけの曖昧な定期を推測で確定しない。

**受入条件**：経由違い・期限切れ・未対応券種が検出される。

<a id="route-006"></a>

### ROUTE-006 追加運賃と定期区間

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R地図§3–4／W08–09

通常運賃と当該定期適用後の追加運賃を分ける。区間内でも対象外事業者・経由・種別なら無料と断定しない。単純な運賃差引きで代用せず対応プロバイダーの契約を検証する。

**受入条件**：区間内、区間外、連絡定期、経由違い、バス、期限切れ、未設定で期待した状態になる。

<a id="route-007"></a>

### ROUTE-007 時間内・追加費用内の寄り道

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R地図§3

定期区間内、追加費用なし、30分以内などの条件と最終目的地への到着を同時に満たす候補を探す。寄り道の移動増分と滞在時間を分けて足す。

**受入条件**：移動5分＋滞在20分を5分の寄り道とは表示せず、帰宅の到着制約も守る。

<a id="route-008"></a>

### ROUTE-008 共有情報の由来

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R地図§3／R一緒§1

友人の過去の実訪問と保存・おすすめを区別し、現在位置と誤解させない。元情報の取消に応じてクエスト・経路説明を失効または再計算する。

**受入条件**：過去の訪問を「いま友人がいる」と表さず、取消した理由が候補に残らない。

<a id="route-009"></a>

### ROUTE-009 制約と不明値

重要度：必須 ／ 工程：G1/G3 ／ 由来：既存要件  
出典：R地図§4／S実装§8

必須条件は満たす・満たさない・不明を区別し、不明を満たしたことにしない。候補なしの場合も利用者に黙って階段や費用等の条件を緩めない。

**受入条件**：必須の座席・通行可否・到着条件が不明なら成立済み経路へ混ぜず不足を返す。

<a id="route-010"></a>

### ROUTE-010 データ寿命と再検索

重要度：必須 ／ 工程：G3 ／ 由来：今回の追加・変更提案  
出典：R地図§6／S実装§12

時刻表・運賃・運行・営業時間の版と更新時刻を保持し、保存した旅行案は実行前に必要な再検証を行う。リアルタイム情報のないAPIをライブ運行保証としない。

**受入条件**：古い保存案を開くと再確認対象が分かり、閉店・運休等の取得失敗を空の正常結果にしない。

## SOC：共有と比較

<a id="soc-001"></a>

### SOC-001 目的・場所から検索

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§1

目的、場所、または両方から公開・共有体験を探す。友人やインフルエンサーは任意フィルターとし、友人ゼロでも使える。

**受入条件**：「休憩」「この周辺」の単独・複合検索で利用可能な結果が出る。

<a id="soc-002"></a>

### SOC-002 友人の接続・解除

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§1

本人が接続・解除できる。接続方法は招待コードを推奨仮定とし、友人になっただけで全履歴を共有しない。

**受入条件**：接続直後は未指定の写真・原文・軌跡が見えず、解除後の範囲を確認できる。

<a id="soc-003"></a>

### SOC-003 項目別・相手別共有

重要度：必須 ／ 工程：G1/G3 ／ 由来：既存要件  
出典：R一緒§1・6

場所、経路、用途、理由、写真、原文、集約活動範囲を個別に選び、相手/公開範囲とプレビューを確認する。保存や作成を自動投稿としない。

**受入条件**：用途だけ共有した場合、原文や精密位置を参照経由でも取得できない。

<a id="soc-004"></a>

### SOC-004 実用的な体験

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§1

ラーメンの「にんにく多め」の注文、服を買う巡回ルート、インフルエンサーの散歩等を具体的なコツとして保存する。実訪問、感想、推奨、店の現在の事実を混ぜない。

**受入条件**：注文の工夫・巡回順・出典・訪問日が閲覧でき、過去の感想を現在の営業時間としない。

<a id="soc-005"></a>

### SOC-005 ルートの作成・共有

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§1

作者、テーマ、立寄り先、順序、コツ、時間の根拠、更新日を持つルートを作成・保存・編集・共有・取消できる。AI改変は原ルートの別版として示す。

**受入条件**：作者の投稿時間と現在の再計算ETAが区別され、編集で作者の原文が上書きされない。

<a id="soc-006"></a>

### SOC-006 意味の比較類型

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§2

同じカフェの勉強/会話、同じ駅の別ランチ、川辺/本屋の気分転換、同じ公園の休憩、見慣れた建物の新しい用途という全例を扱う。場所一致と用途・理由一致を分ける。

**受入条件**：5つの例をそれぞれ根拠付きで表示し、施設カテゴリ一致だけで結論を作らない。

<a id="soc-007"></a>

### SOC-007 比較の条件

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§2

場所・状況・用途を入口として、人物、期間、平休日、時間帯、同行者で絞る。不明な条件を指定条件に一致したことにしない。

**受入条件**：同じ人でも平日/休日、一人/同行者ありで違う比較を保持できる。

<a id="soc-008"></a>

### SOC-008 左右と地図の対応

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§2／A17

自分・相手・重ね合わせと左右のカードを連動させる。別都市はそれぞれの地図へ到達でき、意味の対応を都市間の移動経路線として描かない。

**受入条件**：カード選択で正しい側の地図が動き、名古屋と東京を歩行案内の線で結ばない。

<a id="soc-009"></a>

### SOC-009 根拠と対応の訂正

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§2／A19

共通点・違い・本人の説明とAI対応案を表示し、合う/違うを訂正できる。同じ入力版だけでは却下した対応を再生しない。情報不足は共通点なしと区別する。

**受入条件**：却下が再読込み後も残り、引用権限が消えた根拠を閲覧できない。

<a id="soc-010"></a>

### SOC-010 友人レンズからの行動

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§3

比較から友人レンズで見る、そこへ行く、別の街で試すへつなぐ。実人物の共有視点と架空のペルソナ提案を明示する。

**受入条件**：選んだ元体験・用途・理由が移し替え画面へ引き継がれる。

<a id="soc-011"></a>

### SOC-011 一緒のコース

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§4

本人と同行者の希望を混ぜて消すのでなく、各人の希望と共通の必須条件を示し、例えば本屋と水辺の両方を含むコースを選ぶ。合意前の送信はしない。

**受入条件**：片方の必須条件が満たせないと説明し、候補を選んだだけでは相手に送られない。

<a id="soc-012"></a>

### SOC-012 体験の持ち帰り

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§5

試した人が自分の写真・用途・理由・感想を新たに保存する。元の作者の体験と自分の体験を分離し、共有返信には相手と項目の確認を置く。

**受入条件**：自分の感想が次の自分の推薦に使われても作者の説明が変わらない。

<a id="soc-013"></a>

### SOC-013 体験で返信

重要度：望ましい ／ 工程：G3 ／ 由来：今回の追加・変更提案  
出典：R一緒§5の拡張

体験レシピを試した結果を、維持できたもの・変えたもの・自分に合った点として返信する。位置や原文を公開しなくても返せる。人数やいいね数で正しさを確定しない。

**受入条件**：受信者が共有許可された差分だけ読め、返信取消も反映される。

<a id="soc-014"></a>

### SOC-014 共有取消の表示

重要度：必須 ／ 工程：G1/G3 ／ 由来：既存要件  
出典：R一緒§6／A21–23

検索、比較、保存、クエスト、AI会話、実行中の生成を含め、取消済み情報をアプリ管理下で再利用しない。相手が新しく体験した記録は別扱いとする。

**受入条件**：開いている画面と生成完了直前のケースでも失効版が公開されない。

## TRF：体験の移し替え

<a id="trf-001"></a>

### TRF-001 体験レシピへの分解

重要度：必須 ／ 工程：G3 ／ 由来：今回の追加・変更提案

元体験を目的、役割、順序、理由、必須条件、変更可能な要素、移せない記憶に分解し、本人が確認できる「体験レシピ」にする。抽出元と仮説を保存する。

**受入条件**：「本屋→水辺」を店舗カテゴリの置換だけにせず、前後の意味と理由を編集できる。

<a id="trf-002"></a>

### TRF-002 遷移を含めた移し替え

重要度：必須 ／ 工程：G3 ／ 由来：今回の追加・変更提案  
出典：Sデータ§6の拡張

場所の役割だけでなく、例えば刺激を得る→視界の開けた場所で落ち着くという段階間の関係も候補に用いる。同じ施設を再訪する行程は別の役割ノードで表す。

**受入条件**：立寄り先が同じでも順序を入れ替えると元体験の維持評価が変わる。

<a id="trf-003"></a>

### TRF-003 候補取得と検証の分離

重要度：必須 ／ 工程：G3 ／ 由来：既存設計案を継承  
出典：S実装§8

役割に合う候補を集めた後、地理・営業時間・費用・歩行/交通・必須条件を独立に検証する。LLMが文章を書けることを到達可能性の証明にしない。

**受入条件**：候補の実在と経路を確認し、必須条件が欠けた候補を成立済みから除ける。

<a id="trf-004"></a>

### TRF-004 忠実さと自分適合

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§3／A28

元の人の視点を保つ案と自分向けの案を切り替える。忠実さ、自分への適合、根拠充足率は別の値とし、重みは設計仮定として明示する。

**受入条件**：同じ候補集合でモードを切り替えると理由と順位が説明可能に変わる。

<a id="trf-005"></a>

### TRF-005 移し替えの明細

重要度：必須 ／ 工程：G3 ／ 由来：今回の追加・変更提案  
出典：R一緒§3の具体化

維持した役割・条件、変更した場所・手段、再現できない記憶や人物、未確認情報を対照表示する。未校正の数値を「再現度87%」のような確率にしない。

**受入条件**：選ばれた行程の全要素が元体験か本人の変更へ遡れ、不明が一覧で読める。

<a id="trf-006"></a>

### TRF-006 共同選択と不成立

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§3–4／A29–32

目的地や時間が両立しなければ、何を変更すると成立するかを提案し、承認されるまで条件を変えない。思い出・友人関係・その日固有の気持ちの再現は保証しない。

**受入条件**：条件なしで候補を捏造せず、変更前後を明示する。

<a id="trf-007"></a>

### TRF-007 OpenUASの役割

重要度：必須 ／ 工程：G3 ／ 由来：今回の追加・変更提案  
出典：今回ユーザー希望／W03–04

OpenUASを異都市で都市利用の似た地域を探す候補取得の事前情報として使う。施設カテゴリだけでは探しにくい地域の候補を広げ、最後は個別の用途・条件・現在データで検証する。

**受入条件**：同じ評価コーパス・取得予算でOpenUASあり/なしの候補と適合を比較できる。

<a id="trf-008"></a>

### TRF-008 OpenUASの意味境界

重要度：必須 ／ 工程：G0/G3 ／ 由来：今回の追加・変更提案  
出典：W03–04

共通のアンカー整合性・版・対象時期・対象範囲を検証する。地域ベクトルを性格、店内の静けさ、リアルタイム混雑、災害危険度、個人の嗜好ベクトルと同一視しない。別々の埋込み空間を直接内積しない。

**受入条件**：メッシュ・時期・モデル版・補完フラグから根拠を示し、範囲外はUASなしと表示される。

<a id="trf-009"></a>

### TRF-009 補完メッシュと広域性

重要度：必須 ／ 工程：G3 ／ 由来：今回の追加・変更提案  
出典：W03–04

50mメッシュでも250m由来の補完は粗い根拠として扱う。地域の用途類似から個別店の席・騒音等を推定しない。単純カテゴリ検索からの候補も残して、UASが全候補を独占しない。

**受入条件**：同じ250mから補完した複数メッシュを独立した高解像度証拠として数えない。

<a id="trf-010"></a>

### TRF-010 地域と利用権

重要度：必須 ／ 工程：G0 ／ 由来：今回の追加・変更提案  
出典：W03–04／S実装§3

主デモの比較は名古屋と東京を推奨し、実際のメッシュ収録を確認する。横浜・箱根は元の地域候補として保持するが、UAS収録を未確認のままあるとしない。配布・コンペ・商用の権利を分けて確認する。

**受入条件**：地域manifestとライセンス記録があり、未収録地域のベクトルが捏造されない。

<a id="trf-011"></a>

### TRF-011 体験後の更新

重要度：必須 ／ 工程：G3 ／ 由来：既存要件  
出典：R一緒§5／A33

選択・訪問・見送り・感想を結び、見送り理由を好みと機械的に同一視しない。新しい本人の説明で次の候補や条件を更新する。

**受入条件**：行けなかった理由が時間不足なら店嫌いへ学習せず、条件を変えると候補に戻れる。

## SELF：自己理解

<a id="self-001"></a>

### SELF-001 今日と過去の振り返り

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R自己§1

今日の時系列・地図を見て過去日へ移動できる。候補・確定・不明・記録なしを区別し、見えていない移動を捏造しない。

**受入条件**：欠測のある日、記録ゼロの日、本人申告だけの日を区別して閲覧できる。

<a id="self-002"></a>

### SELF-002 用途と理由の発見

重要度：必須 ／ 工程：G2 ／ 由来：既存要件  
出典：R自己§2

川辺と本屋がともに気分転換でも、視界が開けることと本に囲まれることという理由の差を残す。誘導的な質問でAIが決めた性格へ誘導しない。

**受入条件**：共通用途と異なる理由が同時に保存・表示される。

<a id="self-003"></a>

### SELF-003 条件を限った訂正

重要度：必須 ／ 工程：G1/G2 ／ 由来：既存要件

「この日は急いでいただけ」の適用をその体験へ限定する。過去の記憶と今の好みを両立させ、有効な本人訂正をAIが黙って解除しない。

**受入条件**：現在の訂正で過去の体験文が消えず、再推論後も訂正範囲が守られる。

<a id="self-004"></a>

### SELF-004 週・月・年の統計

重要度：必須 ／ 工程：G2 ／ 由来：既存要件

移動、訪問、新しい場所・地域、時間、用途・理由・変化を集計し、記録率や不明分を示す。位置記録がない日を活動ゼロとみなさない。

**受入条件**：異なる記録量の週を比較する際に欠測が見え、移動距離の不明を0にしない。

<a id="self-005"></a>

### SELF-005 診断機能の内容

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：R自己§4の具体化

パーソナリティ診断を削除せず「街との付き合い方：状況別の行動プロファイル」として実装する。固定型や臨床診断ではなく、どの状況で何を優先しやすいかという検証可能な仮説を示す。

**受入条件**：各記述に対象状況、根拠、反例、更新日、未確認点が付き、データ不足では保留される。

<a id="self-006"></a>

### SELF-006 申告・選択・制約・結果

重要度：必須 ／ 工程：G1/G2 ／ 由来：今回の追加・変更提案  
出典：W10–12／今回ユーザー指示

本人の申告、実際に提示した選択肢、その時点の実行可能性、選択、訪問後の目的適合を別に保存する。行かなかっただけの場所を嫌いと学習しない。

**受入条件**：提示されなかった候補・休業候補・通学上必須の訪問を自由な好みと混同しない。

<a id="self-007"></a>

### SELF-007 小標本での選好モデル

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：W10–12

状況との交互作用を含む少数の解釈可能な属性を用い、正則化した二者選択モデル等で選びやすさを更新する。LLMは抽出・説明・質問に使い、根拠なしに重みや確信度を作らせない。

**受入条件**：入力とモデル版を固定すると順位を再現でき、データ不足時は強い性格結論を返さない。

<a id="self-008"></a>

### SELF-008 一つだけ聞く能動的質問

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：R自己§2の拡張／W11

候補の順位や解釈を分ける有用な質問を1つ選ぶ。情報利得だけでなく回答負担と機微性を考慮し、回答しない選択も尊重する。初期はルール選択、後に事後分布に基づく選択へ接続できる契約とする。

**受入条件**：答えても候補が変わらない質問を優先せず、同じ根拠の質問を反復しない。

<a id="self-009"></a>

### SELF-009 反例と説明の比較

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：今回提案

「静かだから選んだ」「近いから選んだ」「時間がなかった」等の競合仮説を本人が選び直せる。反例を隠さず、訂正前後で同じ候補集合に対する順位・理由の差を示す。

**受入条件**：文章だけでなく次の選択が変化し、訪問の事実と本人が確認済みの用途は勝手に変更されない。

**反映時の補足**：訂正が評価に影響する入力例で差を検証する。すべての訂正で順位を強制的に変える要件にはしない。順位が同じ場合も、根拠・重み・理由の変更と、その順位を維持した理由を追えるようにする。

<a id="self-010"></a>

### SELF-010 予測の検証

重要度：必須 ／ 工程：G2/G5 ／ 由来：今回の追加・変更提案  
出典：W10–12

振り返りの納得感だけで正しさを判定せず、その後の別場面の選択・目的への適合で仮説を点検する。2体験という既存条件は仮説生成の下限であり統計的な検証完了ではない。

**受入条件**：学習に使った体験と評価体験を区別し、根拠数と評価対象数を別に表示できる。

<a id="self-011"></a>

### SELF-011 望む自分と観測された自分

重要度：必須 ／ 工程：G2 ／ 由来：今回の追加・変更提案  
出典：今回提案

よく行く場所に閉じ込めず、「今日は新しい体験をしたい」等の現在の希望を優先する。習慣的行動と本人が望む探索を別に保持する。

**受入条件**：頻回訪問に反する希望を明示すると条件を守った新規候補が出る。

<a id="self-012"></a>

### SELF-012 日記

重要度：望ましい ／ 工程：G2 ／ 由来：既存要件  
出典：R自己§5

日記として体験を残し、AIの下書きは本人が承認・編集する。出来事、本人の表現、AIの補足を区別し、共有を自動化しない。

**受入条件**：AIが書いた架空の体験が承認なしに日記の事実へ混ざらない。

<a id="self-013"></a>

### SELF-013 発見を戻す

重要度：必須 ／ 工程：G2/G3 ／ 由来：既存要件

本人が確認した用途は建物に、現在の希望・条件は推薦に、許可した内容は比較へ反映する。仮説の成立と訪問の成立を分離する。

**受入条件**：診断の訂正だけで訪問数は変わらず、用途訂正は正しい建物に反映される。

<a id="self-014"></a>

### SELF-014 非医療・非センシティブ推定

地域や移動から疾患、宗教、政治、性的指向等の個人属性を推定しない。性格型・人口内パーセンタイル・医学的改善を検証なしに主張せず、友人の相性をデーティング用途へ転用しない。

**受入条件**：機微な場所の訪問でセンシティブ診断が生成されず、共有プロファイルが本人承認に限定される。

**受入条件**：生成した版・テストした版・導入した版のハッシュが一致する。

### EXT-010 編集範囲とテストの独立

Codexに変更可能なファイルと合成入力を渡し、本体、私有履歴、秘密、独立テストの期待値を変更範囲へ入れない。テスト変更で失敗を成功にしない。

**受入条件**：検証後改変・期待値書換え・権限追加が検出され、有効化できない。

<a id="ext-011"></a>

### EXT-011 能力単位の権限

**受入条件**：未許可の個人データ・外部送信・ローカルネットワーク・親DOMへのアクセスが拒否される。

<a id="ext-012"></a>

### EXT-012 端末実行と隔離

コードと専用画面は端末側の制限実行環境と隔離表示に分ける。Dockerを必須にしない。Workerやiframeを置いただけで通信・無限ループ・メモリ制限が完了したと見なさない。

**受入条件**：停止、出力上限、通信禁止、親表示の無応答回避をSimulator環境で検証する。

<a id="ext-013"></a>

### EXT-013 外部接続の現実性

重要度：必須 ／ 工程：G0/G4 ／ 由来：既存設計案を継承

端末から取得可能な公開情報は端末の許可済み仲介で取得する。CORS未対応や運営秘密キーが必要な接続は事前定義した運営APIで仲介する。任意の新規サーバーコードの実行は従来どおり初期対象外とする。

**受入条件**：CORSやキー未設定を動作済みとして隠さず、生成コードに秘密が含まれない。

GeoJSON、カード、評価、独自表示データ、許可された入力を追加可能とする。任意HTMLを本体へ挿入せず、Schema、サイズ、地域範囲、送信元・nonceを検証する。

**受入条件**：無効な座標・巨大出力・偽メッセージ・スクリプト注入を拒否する。

<a id="ext-015"></a>

### EXT-015 共有・複製・復帰

機能コード・条件と私有データを分離して共有・forkする。独立して許可取得したコード複製と、元情報への利用権は別物とする。元情報を取消したら私有入力を再利用しない。

**受入条件**：コードforkは保持できても元作者の取消済み位置・理由へアクセスできない。

### EXT-016 5形式の情報取込み

**受入条件**：5形式すべてに正しい入力と不正入力の検査があり、PDF読取不能が空の正常データにならない。

<a id="ext-017"></a>

### EXT-017 通常更新とAI修復の分離

通常更新は検証済み変換器で行い、構造変更で失敗した際だけCodex修復候補を作る。通信障害は再試行、意味変更は保留する。最終成功データと時刻を保持する。

**受入条件**：列名変更は独立テストを通して復旧し、単位変更は自動で正当化されない。

**受入条件**：表示終了後の通知未実装を監視中と表さず、再開時に再確認できる。

## DATA：データ・訂正・権限

<a id="data-001"></a>

### DATA-001 ID・版・依存関係

重要度：必須 ／ 工程：G1 ／ 由来：既存設計案を継承  
出典：Sデータ§1–3

体験、理由、訂正、共有、候補、診断、機能結果に所有者・実行領域・安定ID・版と参照フィールドを持たせる。原文と派生結果を分離する。

**受入条件**：一つの理由を訂正すると依存する結果だけが失効し、どの版から生じたか追える。

### DATA-002 本人の訂正を優先

有効な本人訂正を同じ範囲のAI仮説より優先し、体験指定・条件指定・全体指定を区別する。撤回も明示操作とし、推論が自動で撤回しない。

**受入条件**：当日の訂正を全期間へ広げず、変更の競合は409等で確認できる。

<a id="data-003"></a>

### DATA-003 共有投影と現在権限

私有データそのものを公開せず、許可項目の投影を返す。過去版を読む場合も現在の権限を確認する。画像や結果に取消不能な長期公開URLを発行しない。

**受入条件**：IDや過去版のURLを知っていても取消済み本文は取得できない。

<a id="data-004"></a>

### DATA-004 生成中の取消と訂正

長い処理の開始時だけでなく公開直前にデータ版と権限版を照合する。変更済みなら再計算または保留とし、失効した根拠の文章を公開しない。

**受入条件**：生成中に共有を取消しても旧情報の回答が出ない。

<a id="data-005"></a>

### DATA-005 会話履歴への反映

AIへ渡す履歴を毎回許可済み根拠から組み直す。プロバイダー側のスレッド記憶を権限確認なしに継承しない。保存停止設定を全保持ゼロの保証と説明しない。

**受入条件**：取消した引用が古い会話の続きや再質問から再出現しない。

<a id="data-006"></a>

### DATA-006 実体験と複製の境界

重要度：必須 ／ 工程：G3 ／ 由来：既存設計案を継承  
出典：S実装§13／A41

相手が自分で経験した記録は相手の所有とし、元共有取消だけでは消さない。ただし元の取消済み原文や私有情報の引用部分は分離して失効する。

**受入条件**：自分の感想は残り、相手の取消した私有引用だけが表示されなくなる。

<a id="data-007"></a>

### DATA-007 取消の限界とオフライン

重要度：必須 ／ 工程：G1/G5 ／ 由来：今回の追加・変更提案

アプリ管理下の再取得・派生表示を止めるが、既に撮影された画面・外部保存やオフライン端末を遠隔消去できると約束しない。再接続時の失効確認とキャッシュ寿命を設定する。

**受入条件**：オフラインで即時取消できない旨が共有説明にあり、再接続時に失効データが消える。

### DATA-008 位置と文章の機微性

位置フィールドを消すだけでは原文・Exif・時間列から漏れ得るため、共有プレビューとExif除去、集約範囲・時間の粒度を設ける。自宅・学校等の公開は自動化しない。

**受入条件**：用途だけの共有で文章・写真メタデータから精密位置を不用意に出さない。

<a id="data-009"></a>

### DATA-009 認証の境界

ローカル架空人物デモはサーバー発行セッションと共通主体解決で行い、入力owner_idを信用しない。外部公開と実ユーザーの私有データ受付前には本物の認証を接続する。

**受入条件**：デモ人物切替が外部公開されず、他人のowner_id指定で更新できない。

<a id="data-010"></a>

### DATA-010 外部入力と秘密

重要度：必須 ／ 工程：G0/G4 ／ 由来：今回の追加・変更提案

**受入条件**：取得資料内の指示で秘密送信・テスト改変・権限追加が起こらない。

<a id="data-011"></a>

### DATA-011 保存・削除・出力

**受入条件**：削除後のプロファイルを残存根拠から再現でき、削除した情報が学習済みだからという理由で残らない。

<a id="data-012"></a>

### DATA-012 データの権利台帳

**受入条件**：提出資料と配布データに出典と条件があり、未許諾素材が同梱されない。

## DISC：セレンディピティによる関心の発見

ユーザーの「改めて取り入れ」の指示で追加。[実験プロジェクトの確認と接続案](../research/serendipity-project-reuse-2026-09-08.md)に由来する。

<a id="disc-001"></a>

### DISC-001 街の対象から関心を広げる

重要度：必須 ／ 工程：G2 ／ 由来：2026-09-08セレンディピティ取込

建物、場所、写真に写る対象など、本人が注目した街の対象を入口に、具体的な特徴や知識を介して別の関心へつながる発見を提供する。既存の用途・理由に合う推薦と、まだ表明していなかった関心を開く発見を区別する。

**受入条件**：入口の対象、つながり、新しく知る内容を示せる。同じ目的を満たす類似施設だけを並べても本要件の完成としない。

<a id="disc-002"></a>

### DISC-002 説明に働く入口と着地

重要度：必須 ／ 工程：G2 ／ 由来：2026-09-08セレンディピティ取込

短い発見には入口の対象、関係する特徴・機構・来歴等、着地となる具体的知識を持たせる。入口とその役割を削除しても説明が変わらない場合は飾りとして見直す。同じ性質を持つ別の対象でも成立することだけでは棄却しない。

**受入条件**：入口を削った説明との違いを確認でき、話が入口の既知説明だけで終わらない。弱い接続は提示を見送り、文章の流暢さだけで採用しない。

<a id="disc-003"></a>

### DISC-003 一般知識とその場所の事実

重要度：必須 ／ 工程：G1 ／ 由来：2026-09-08セレンディピティ取込

一般的な知識、写真から観察した内容、その場所固有の事実、本人の感想、AIが提案する見方を区別する。特定の建物の歴史や素材、施設情報は対応する根拠を確認する。特定できない写真から場所や物体の正体を断定しない。

**受入条件**：一般原理を特定建物の設計意図として表示せず、場所固有の主張は出典へ遡れる。根拠不足では未確認のまま扱う。

<a id="disc-004"></a>

### DISC-004 知ることと次の行動をつなぐ

重要度：必須 ／ 工程：G3 ／ 由来：2026-09-08セレンディピティ取込

発見の中心を、その場で対象の見方が変わり、もっと知りたくなることに置く。詳しく知る・現地で観察する導線を主にし、別の場所や体験を探す導線はその先の任意操作とする。知識としてのつながりと移動経路を分け、移動には通常の時間・費用・営業・通行等の検証を通す。

**受入条件**：発見の対象・概念を次の操作へ引き継げる。保存・閲覧だけで訪問済みや建物成長にせず、未検証の直線を案内として出さない。

<a id="disc-005"></a>

### DISC-005 提示と既知概念の履歴

重要度：必須 ／ 工程：G1 ／ 由来：2026-09-08セレンディピティ取込

候補生成、実際の提示、本人の閲覧・保存・反応を別々に記録する。以前に提示した対象と概念を参照して同じ説明の反復を避け、生成しただけの内容を既読・既知とは扱わない。

**受入条件**：未提示の失敗生成で露出履歴が増えず、同じ知識を別の建物名へ置き換えて繰り返さない。既知であるという本人の回答も別に保持する。

<a id="disc-006"></a>

### DISC-006 探索の主導権

重要度：必須 ／ 工程：G2 ／ 由来：2026-09-08セレンディピティ取込

発見は本人が開く操作を基本とし、余裕がある場面に限って提案する。余裕の判定と提案頻度は詳細設計で定め、時間の余りだけで受取り希望を断定しない。本人が探索を選んだ場面では苦手な分野も候補に含めるが、通常の提案へその許可を持ち越さない。明示した表示禁止・停止は保持し、苦手という評定と区別する。通常の案内を暗黙に寄り道へ変更しない。元実験の低関心優先や固定重みを日常利用へそのまま継承しない。

**受入条件**：提案を見送っても記録・案内は使える。未関心、未知、明示的な拒否を区別し、拒否範囲の変更は本人が選べる。

### DISC-007 新しい関心を持ち帰る

重要度：必須 ／ 工程：G3 ／ 由来：2026-09-08セレンディピティ取込

本人が興味を持った発見を、その入口・体験・分野とともに「自分を知る」で振り返れるようにする。友人へは本人が選んだ範囲で共有し、同じ場所を別の観点で見る入口にする。機能が必要になった場合は関連するプラグインへつなげる。

**受入条件**：一つの発見から本人が表明した関心と共有範囲を追え、クリックだけで長期の好みや性格を確定しない。共有を取り消した説明が再利用されない。

<a id="disc-008"></a>

### DISC-008 発見の価値を測る

重要度：必須 ／ 工程：G5 ／ 由来：2026-09-08セレンディピティ取込

知らなかったこと、興味が湧いたこと、後に調べたり観察・訪問したことを分けて評価する。説明の正しさと入口の寄与、提示負担、既出概念の反復も確認する。評価質問を通常利用で毎回必須にするかは別の設計判断とする。

**受入条件**：生成成功率や文章の自己採点を関心拡張の実証としない。通常推薦との比較で実用性・発見・後続行動・失敗を別々に記録する。
