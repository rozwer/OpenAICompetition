# 仕様の論点

この文書は、「育てる地図」の仕様をこれから議論するための問いを、大分類だけで並べたものである。

問いへの答え、参考資料に書かれた案、既存の技術名や数値を既定値として扱わない。
ここでは決定を誘導せず、議論で確認する対象を漏らさないことを目的にする。

議論の土台として、[詳細要件案](../要件/詳細要件案.md)と[用語集](../要件/用語集.md)を参照できる。
これらも未確定であり、問いへの結論を先に決めるものではない。

## 画面・体験

- 利用者は最初に何をし、どの体験を経て「自分の地図が育った」と感じるか。
- 体験の中心に置く画面や操作は何か。
- 一人で使う体験と、他者の地図を見る体験をどのように関係付けるか。
- 今回の範囲に含めない体験は何か。

## データ

- 最低限、何を記録・表示・更新できれば体験が成立するか。
- 記録、本人の説明、システムの推定をどのように区別するか。
- 訂正、削除、共有、非公開の扱いをどこまで定めるか。
- 位置や時間など、扱うデータの粒度と保持範囲をどうするか。

## AI・外部連携

- AIに任せる役割と、利用者が確認・修正する役割をどこで分けるか。
- 外部サービスや外部データを、どの体験に使うか。
- 外部接続が使えない場合に、どの範囲を代替・再現できればよいか。
- 生成結果の根拠、状態、失敗を利用者にどう伝えるか。

## 対象端末・利用環境

- 今回、利用者が実際に操作する対象端末と画面環境は何か。
- 端末固有の機能や入力を、今回の範囲に含めるか。
- 端末やブラウザの違いに対して、どこまで同じ体験を求めるか。

## デモ範囲

- デモで最初から最後まで見せる一連の流れは何か。
- デモ用の人物・場所・データをどのように用意するか。
- デモで実際に接続するものと、再現・モックで扱うものをどう分けるか。
- 発表時間内に、何を見せれば中心体験が伝わるか。

## 受入条件

- 仕様が決まった後、利用者が確認できる成功状態は何か。
- 画面だけでなく、保存・更新・連携のどの結果を確認するか。
- 必須の成功条件と、余力があれば確認する条件をどう分けるか。
- 失敗、未接続、未回答などの状態を、どこまで扱えればよいか。
